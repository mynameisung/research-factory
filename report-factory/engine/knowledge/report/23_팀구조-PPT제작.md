# 23. 팀 구조 — PPT 직접 제작 (업무 B)

설계 2026-08-22. 에스원 비상주 건에서 실측한 결함 5건으로 도출했다.
"하나의 에이전트가 다 하려니 못 한다"는 관찰이 출발점인데, 처방은 '에이전트를 늘린다'가
아니라 **역할별로 갈라 보면 에이전트가 답인 곳이 2곳뿐**이라는 것이다.

| 실측 결함 | 원인 유형 | 처방 |
|---|---|---|
| Base 라벨 「전체」 28장 | 규칙 부재 | 정본 스키마 필드 + 기계 검사. 에이전트를 쓰면 28장 중 27장만 잡는 날이 온다 |
| 요약 첫 패널 정렬 1칸 | 코드 버그 | 코드 수정 + 기계 검사 |
| 멘트 63~74자 줄바꿈 복불복 | 한계 미측정 | 길이 상한 규칙(≤60자) |
| 「의사결정자 개인 1인」 과잉해석 | 판단 결함 | **에이전트** (적대 감사) |
| 주제명이 카피(「무엇이 중요한가」) | 명명 규칙 부재 + 판단 | 스키마(short) + **에이전트** |

## 원칙 3

1. **생성은 스크립트, 판단은 에이전트, 결정은 사람.**
   매번 전부 잡혀야 하는 검사(수치 대조·패키지·라벨 규칙)에 에이전트를 쓰면 비결정성이
   결함이 된다. 판단이 필요한 곳(렌더가 어떻게 보이는가 · 주장이 근거를 갖는가)에만 쓴다.
2. **PPT 팀은 문장을 짓지 않는다.** 멘트·제목·Base 라벨의 정본은 가이드 산출물
   (slide_facts.json)이고 PPT 는 옮겨 심는다. 결함 발견 시 반송 대장
   (`2_보고서작성/work/반송_가이드팀.md`, ID `R-PPT-NNN`)에 적고 기다린다.
   여기서 지어 넣는 순간 두 팀 산출물이 어긋나고 대조가 불가능해진다.
3. **에이전트 분리보다 시야 분리가 먼저다.** 과잉해석 멘트의 원인은 '쓰는 쪽이 원자료
   전부를 볼 수 있었던 것'이다. 에이전트를 다섯으로 나눠도 각자에게 전부 보여 주면 같다.

## 가이드 팀과의 접점 (2026-08-22 양 세션 합의)

- **소유권**: PPT 산출물·스크립트·`2_보고서작성/HANDOVER.md` = PPT 세션 /
  가이드 산출물·정본 데이터(slide_facts·tables) = 가이드 세션.
  상대 HANDOVER 직접 수정 금지 — 메시지로 넘긴다.
- **스키마 로드맵**: 1단계(additive) `slides[].base_label`·`slides[].short` →
  2단계 `summary_map`(claims: 문장 ↔ 근거셀)·`conclusion_map`(조사목적 대응).
  V5 는 claims 를 반증 대상으로 쓴다.
- **멘트 길이 정책**(정본 소관): 본문 멘트 줄 ≤60자(K-10). 요약·결론 줄은 60자를 강제하지 않고
  렌더 한 줄 74자를 넘을 때만 알린다(R-198 · R-205 — 「요약 헤드라인 ≤40자」는 R-130 과 함께 폐기).
  근거: 멘트 상자 한 줄 실측 74자(32.0cm·맑은 고딕 12pt).

## 색이 뜻을 갖게 한다 — 막대 색 규칙 (사용자 확인 2026-08-23)

| 대상 | 색 |
|---|---|
| **의뢰처의 상품·서비스가 낮게 평가된 문항** | 회색 |
| 그 밖 전부 (기본·현황·긍정) | **주색**(클라이언트 primary) |

**기준은 어조가 아니라 대상이다.** 「어려움」·「애로」가 붙었다고 회색으로 빼면 안 된다 —
응답자의 pain point 는 의뢰처에게 **기회**이고, 회색으로 빼는 순간 기회가 문제로 보인다.
회색은 의뢰처가 낮게 평가받은 자리에만 쓴다.

> 실례(에스원 260822): 어조로 훑어 5장을 회색 처리했는데 사용자 정정으로 3장이 됐다.
> 빠진 둘 — `B1 어려움을 느끼는 업무` · `B1-1 공사 애로` — 는 신상품이 파고들 지점이었다.

자동 판정은 **문항코드 목록으로 좁게** 잡고 애매하면 주색으로 둔다. 실무에서는 제작팀이
판단하는 영역이라 과하게 자동화하지 않는다.

## 표에 싣지 않는 행

- **「계」** — 100.0 이 배너마다 반복될 뿐 정보가 없다. 게다가 차트 범주를 한 칸 밀어
  **막대와 라벨을 어긋나게** 한다(고정 차트 프레임 + 범주 수 = 데이터 행 수 전제).
- 평균은 표 행이 아니라 **그래프 상단 Text** 로 나간다.

## 척도 범례는 설문지 기준으로 전 단계를 세운다

통계표는 **응답이 0인 단계를 행째로 지운다.** 그대로 범례를 만들면 「매우 불만족」이
사라져 독자는 4점 척도로 물은 줄 안다. 범례는 *무엇을 물었는가*를 보여 주는 자리이므로
`questionnaire.scale.labels` 로 전 단계를 세우고, 데이터 없는 단계는 자리만 지킨다.

★ 단, **라벨의 정본은 통계표**다. 설문지 원문에 오타가 있을 수 있다
(실측 D4: 보기 2와 4가 같은 문장). 설문지는 *빠진 단계의 이름만* 채운다.

## 요약 패널의 배너는 두 가지 그림이다 (실측 2026-08-24)

정본(`summary_map`)의 패널 `chart` 문자열이 **어느 쪽인지 골라서 적는다.**

| 정본 표기 | 그림 | 읽는 목적 |
|---|---|---|
| `배너 표 (군)` | 라벨 1열 + 배너 N열 숫자표 | 집단별 **값**을 대조한다 |
| `배너 가로 누적 100% 막대 (군)` | 막대 = 배너 열, 조각 = 보기 | 집단별 **분포가 어디로 몰리는가** |

갈림길은 정본 문자열이지 데이터 모양이 아니다. 「열 합이 100이면 누적으로 그리자」 같은
추측 규칙을 세우면 같은 모양의 「배너 표」 패널까지 끌려 들어간다. 합이 100인지는
**판정이 아니라 검문**으로만 쓴다 — 누적 지정인데 안 닫히면 경고하고 표로 되돌린다.

> 왜 누적이 나은가: 「신상품 지불 용의 금액 × 관리 운영 방식」을 숫자표로 놓으면 16칸이고
> 어디가 봉우리인지 눈으로 세야 한다. 누적 막대로 놓으면 직접 관리는 15만원 미만(31.8),
> 외부 전면 위탁은 25~35만원(47.1) 으로 **봉우리가 오른쪽으로 이동하는 것이 한눈에 보인다.**
> 「적정 가격은 하나가 아니라 관리 방식마다 다름」이라는 헤드라인이 그림으로 증명된다.

조각을 쌓는 순서는 **사다리 아래쪽이 왼쪽**이다. R-068 은 「통계표 역순」이라 적혀 있지만
그건 척도 통계표가 상위부터 내려오기 때문에 나온 결과다 — 금액 구간표처럼 이미 오름차순인
표에 역순을 걸면 고액이 왼쪽에 와서 사다리가 뒤집힌다. 표의 방향을 읽고 맞춘다.

전환할 때 함께 고쳐야 하는 세 가지(레이블 위치·값축 최댓값·범례)는 R-139·R-140 에 있다.
