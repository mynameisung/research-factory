# 40. 웹테스트 — 실사 화면 검수 (업무 C)

설문지가 웹조사 화면으로 구축되면, 실사에 들어가기 전에 연구원이 화면을 한 문항씩 넘기며 설문지대로 됐는지 본다.
이 문서는 그 일의 성질과, `/웹테스트` 가 무엇을 기계로 하고 무엇을 사람에게 남기는지 적는다.
원천은 2026-07-23 패널조사 연구원(설문 실사 담당) 통화 정리다.

## 1. 일의 흐름 (사람이 하던 방식)

1. 연구원이 워드 설문지(예: 자동차 CSI, 36쪽)를 써서 실사 프로그래밍 담당자에게 넘긴다.
2. 담당자가 설문을 웹(엠브레인 isurvey, classic ASP)에 구축한다.
3. 연구원이 브라우저에서 **한 문항씩 클릭하며** 검수한다. 한 페이지 = 한 문항, 「다음 → 다음 → …」.
   **뒤로가기가 되지 않아** 시나리오 하나가 틀리면 처음부터 다시 돈다.
4. 오류를 **엑셀 수정요청서**로 정리해 담당자에게 보낸다(「적용 안 돼 있어요, 적용 필요합니다」).
5. 고객사도 따로 테스트하고, 문항 추가·삭제 요청이 중간에 계속 들어온다(엑셀 No.11 「신규 문항 2개 추가」).

기존 워크어라운드: 챗봇에 설문지를 넣고 「최소 테스트 시나리오」를 받아 엑셀 매트릭스(행 = 문항, 열 = 시나리오 1~8)로
정리한 뒤 그 표를 보며 손으로 클릭했다. `/웹테스트` 는 이 매트릭스를 설문지 정본에서 기계로 뽑고, 클릭도 기계가 한다.

## 2. 검증할 로직 7종

| 개념 | 설명 | 설문지 표기 | 도구가 잡는가 |
|---|---|---|---|
| SQ(스크리닝) | 설문 앞부분 자격 문항. 나이·성별·가입 상품 등 | SQ1~SQ8 | 노출·이탈로 간접 검증 |
| 이탈(스크린아웃) | 특정 보기를 고르면 조사 종료 | 「프로그」「면접 중단」「→ 조사 중단」 주석 | **잡는다** — T_ 시나리오, TERMINATE_MISMATCH |
| RANGE | 입력값 범위 제한 | 「SQ8 RANGE」「[RANGE: 18~99]」 | 최솟값만 넣는다. 경계값은 사람 |
| 클래스·케이스 분기 | 앞 문항 답에 따라 뒤 문항의 노출·보기 수가 달라진다 | 「[BASE: SQ3=1]」「SQ3=1 응답자만」 | **잡는다** — H_ 시나리오, QUESTION_MISSING/UNEXPECTED. 보기 수 차이는 OPTION_* |
| 파이핑 | 앞 문항 답이 뒤 문항 문장에 들어간다 | 「[# SQ26 응답값 파이핑 #]」 | **잡는다** — PIPING_MISSING (기대값 = 고른 보기 문구) |
| 보기 카드(이미지) | 답에 따라 노출되는 이미지 카드가 달라진다 | 별첨 PPT | 못 잡는다. `images[]` 만 덤프, 캡처로 사람이 본다 |
| 보기 로테이션·고정 | 보기 순서가 무작위, 일부는 고정 | 「로테이션」「고정」 | 순서 다름만 OPTION_ORDER(참고). 무작위성은 사람 |

문구 오탈자·보기 누락·보기 추가·수정 미반영은 로직이 아니라 **대조**로 잡는다(TEXT_MISMATCH · OPTION_MISSING · OPTION_EXTRA).

## 3. 실사 엔진의 성질 (엠브레인)

- 패널 사이트 `panel.co.kr` 은 SPA(jQuery 1.11 + require.js). 조사 목록 카드 → 참여.
- 설문 엔진 `isurvey.panel.co.kr/common_mail.asp?alias=…&panel_id=…` 은 **classic ASP**. 메일 링크로 진입, 랜딩(조사명·기간·소요 시간·적립금) → 「조사참여하기」 → 한 문항씩.
- **패널 계정 로그인이 필요**하고 접속 권한이 제한적이다. 스킬은 로그인을 사람에게 맡기고 세션만 재사용한다.
- 한 계정이 한 번만 응답하게 막힐 수 있다. 시나리오를 여러 번 돌리려면 테스트 모드 URL 이나 테스트 계정이 필요하다 — 사람이 확보한다.
- 고객사마다 설문지 워드 양식이 다르다. 파서(`parse_questionnaire.py`)는 유형 분류 기반이라 놓치는 문항 코드 변형이 있다. 놓친 것은 JSON 을 손으로 보탠다.

## 4. 시나리오 행렬의 규칙

- **S0 기본 경로**: 원천 문항마다 「가장 많은 딸린 문항을 보이게 하는 답」을 골라 끝까지 간다(예: B2=3,4 를 요구하는 문항이 8개, B2=1,2 가 1개면 B2=4). 조사 중단 보기와 「없음」 보기는 피한다. 파이핑 기대값은 여기서 계산한다.
- **B<n>_<문항>**: S0 에서 숨은 문항(서로 배타인 분기의 반대쪽)을 한 번은 밟는다. 원천 답을 그 문항의 조건대로 바꾼다.
- **T_<문항>_<보기>**: 조사 중단 보기를 하나씩 골라 그 자리에서 끝나는지 본다.
- **H<n>_<문항>**: 노출 조건을 하나씩 깨뜨려 딸린 문항이 안 보이는지 본다. 같은 답으로 깨지는 조건은 하나로 합친다. 상한 12개(`--max-branch`).
- 답을 정하지 않은 문항은 순회기가 첫 보기(복수는 앞 두 개, 순위는 앞 세 개, 숫자는 범위 최솟값)로 답한다.
- 읽는 조건 표기: `SQ1=1` · `B2=3,4` · `B1 = 3 or 5` · `D7=4~5` · `C4 = 1) ~ 7)` · `A2-a ≠ 1)` · `C1 ≥ 1개 이상` · `(B1-1 1)≠0) or (B1-1 3)≠0)`(복수 문항의 항목 선택). 「|」 뒤 라벨은 버린다.
- 기계가 못 읽는 것: 산문 조건(「SQ3 에서 1 또는 2 응답자 중 A파트 유경험자」), 숫자 입력 문항의 항목값으로 갈리는 조건(TA 의 「B1-1 1)≠0」 = 오피스 면적 입력값). 이런 문항은 `unparsed_conditions`·`never_visited` 로 보고되고 사람이 답을 정한다.
- 연구원이 늘 쓰던 인구통계 시나리오(남성·서울·20대·가입자 등)는 S1… 으로 보탠다. 기계 시나리오는 로직 검증용이고, 사람 시나리오는 대표 응답자 검증용이다.

## 5. 수정요청서 양식

| 열 | 내용 |
|---|---|
| No | 일련번호 |
| 시나리오 | 잡힌 시나리오(여럿이면 `S0·H1_SQ1`) |
| 문항 | 문번호 |
| 구분 | 종류 코드(QUESTION_MISSING 등) |
| 심각도 | 치명 · 경고 · 참고 |
| 현상 | 정본 「…」 / 웹 「…」 |
| 요청 | 「문구 정정 요청」「노출 조건(BASE) 적용 요청」 등 정형 문구 |
| 페이지 | 순회 페이지 번호(캡처 파일과 같다) |

개발 담당자가 받는 문서이므로 **결함 하나에 한 줄**이다. 사람이 「정상」으로 판정한 행은 엑셀에서 지운다(도구를 다시 돌려 없애지 않는다).

## 6. 이 도구가 하지 않는 것

- 설문지 워드 자동 생성 — 시도했으나 검토가 필요한 수준이었다.
- 무한캔버스 플로우 뷰(Figma 식 분기 시각화) — 별도 플랫폼 과제. `시나리오_매트릭스.md` 가 그 축약판이다.
- 크롬 확장 방식 순회 — Playwright 로 대체. 실제 크롬 세션이 필요해지면 `--headed` 로 사람이 로그인한 뒤 세션을 저장한다.

## 7. 도구

| 도구 | 입력 → 출력 |
|---|---|
| `webtest_scenarios.py` | questionnaire.json → 시나리오.json · 시나리오_매트릭스.md |
| `webtest_walk.py` | URL + 시나리오.json → 덤프_<ID>.json · 캡처_<ID>/ · html_*.html (Playwright · Chromium) |
| `webtest_compare.py` | questionnaire.json + 시나리오.json + 덤프 → findings.json · 수정요청서_<날짜>.xlsx · 대조요약.md |
| `webtest_selftest.py` | 모의 설문(`webtest_fixture/`)으로 세 도구를 실제 브라우저에서 시험. 심은 결함 3종을 잡아야 통과 |

사이트 선택자는 `webtest_walk.py` 의 `PROFILES` 에 엔진별로 둔다(`generic` · `isurvey`). 첫 순회의 `--save-html` 로 맞춘 뒤 고정하고 `/개선공유` 로 올린다.
