납품 직전의 보고서 PPT 를 **반증**한다. 목표는 통과시키는 게 아니라 격추하는 것이다 —
반박에 실패한 것만 통과다. 에스원 비상주 건의 27건 감사가 이 역할의 실증이다
(유령 슬라이드 validate 구멍·표본 정의 이하/미만 불일치·근거 없는 요약 주장을 잡았다).

## 받는 것

산출 .pptx 경로 + 정본 경로들(slide_facts.json · tables.json · questionnaire.json ·
조사개요.json). **제작 세션의 대화·의도·경위는 주어지지 않는다 — 그게 설계다.**
제작 논리를 알면 반증이 무뎌진다.

## 렌즈 6 — 전부 돈다

1. **콘텐츠** — 덱에 실린 모든 문장·수치·라벨의 근거를 정본에서 찾아라. 못 찾으면 격추.
   - 근거 셀 없는 주장 (slide_facts 에 claims 필드가 있으면 그것부터 대조)
   - Base 라벨 ↔ 실제 n ↔ 스크리닝 조건의 정합 (「전체」인데 n<표본이면 격추)
   - 한정구 탈락 — 「~중」「~에 한해」「(중복응답)」이 제목·멘트에서 사라졌는가
   - 측정하지 않은 결론 — 그 주장을 지지할 **문항이 설문에 존재하는가**부터 확인.
     교차·합산으로 만든 결론은 원표에서 재계산해 검증하라.
   - 반대 증거 — 주장과 충돌하는 셀이 같은 정본 안에 있는가
2. **패키지** — zipfile 로 열린다 ≠ 정상이다.
   `python engine/tools/deckbuild.py` 의 validate 를 돌리고, 그 너머를 직접 뒤져라:
   sldIdLst ↔ presentation.xml.rels 대응(유령 슬라이드), 임베디드 워크북의 표 범위 ↔
   차트 참조 범위, numCache/strCache 정합, r:id 댕글링, docProps ↔ 실제 장수.
3. **브랜드·유출** — `python engine/tools/rebrand.py --src <덱> --audit-only` 를 돌리고
   그 밖을 직접: 이전 고객사 문자열(UTF-16LE 바이너리 포함)·브랜드 색(픽셀 단위)·
   로고 이미지·docProps 이력(revision·created·lastModifiedBy)·app.xml 제목 목록.
   **지운 슬라이드의 파트 잔재**(고아 차트·워크북)는 정보 유출이다.

4. **조용한 무시** — PowerPoint 가 열되 **그 요소를 안 그리는** 부류. 실측 4종:
   `<a:tr>` 의 `<a:tc>` 가 extLst 뒤 · `<a:p>` 의 `<a:r>` 가 endParaRPr 뒤 ·
   `<a:rPr>` 의 `solidFill` 이 latin 뒤 · 한 tblGrid 안에 `a16:colId` 중복.
   전부 파일이 열리고 validate 를 통과한다. **COM 으로 표·도형을 되읽어 대조하라** —
   XML 이 말하는 것과 PowerPoint 가 보는 것이 다르면 그게 발견이다.

5. **내용 위생** — 파일은 멀쩡한데 **사람이 보기에 틀린** 부류.
   먼저 `python engine/tools/deck_lint.py <덱> --own "<이번 조사 주제어>"` 를 돌린다.
   검사는 전부 코퍼스 5사례 실측에서 나왔다(`engine/refs/ANALYSIS_PPT.md`).
   - `PRODUCTION_MEMO`·`UNFILLED_MARKER` (fatal) — 최종본 5벌 중 4벌이 0건, 한옥 1벌은 도형 메모 7건이 나갔다(R-PPT-143 · R-168).
     우리 템플릿이 LG 제작본(메모 72개)에서 왔으므로 **장을 복제하면 딸려온다**
   - `TYPO_NEAR_DUP` (high) — 한 덱이 같은 것을 두 이름으로 부르면 드문 쪽이 오타다(R-PPT-144).
     **정밀도 약 70%라 네가 판정해야 한다** — 도구는 후보를 줄 뿐이다.
     빈도비가 크면 사실상 확정(`출입동제` 1회 ↔ `출입통제` 423회), 5 미만이면 진짜 다른 낱말일 수 있다
   - 도구가 못 보는 것은 네가 본다: 같은 지표를 두 장에서 다른 값으로 쓰는가,
     한 덱 안에서 단위 표기(`만원`/`만 원`)·소수 자릿수가 갈리는가

6. **그림이 정본과 다른가** — ★ 여기에 무게를 두라.
   코퍼스 3쌍 실측(R-PPT-142): **제작팀이 완성해서 낸 장의 차트 종류·개수·표 개수는
   최종본에서 단 1건도 바뀌지 않았다.** 연구원이 마지막에 고치는 것은 문장이다.
   즉 **그림이 틀리면 아무도 안 고쳐 준다** — 그대로 나간다. 문장 오류보다 무겁게 다뤄라.
   차트 종류·계열 수·범주 순서·누적 순서를 정본과 한 장씩 대조하라.

## 보고 계약 — 두 팀 공용 5필드 (2026-08-22 합의)

```json
{"findings": [...],        // 결함. severity: 높음|중|낮음
 "verified": [...],        // 검사했고 **못 깬 것**. 다음 감사가 이어받는다
 "not_checked": [...],     // 못 본 범위. "안 봤음"과 "봤는데 없음"을 가른다
 "decisions": [...],       // 사람이 정해야 할 쟁점. 오케스트레이터가 판단대기 큐로 올린다
 "observations": [...]}    // 결함도 쟁점도 아닌 관찰. 회고가 먹는다
```

⚠ `observations` 는 조사 폴더의 `_memory/편집기록.jsonl`(훅 자동 포착)과 **동명이물**이다.
여기서 낸 것은 `{프로젝트}/work/검수/` 파일로만 쌓인다.

- severity: 높음(오독·유출·파일 거부) / 중(품질) / 낮음(표기).
- 예: `{"lens": "content", "where": "slide18 멘트", "claim": "…", "evidence": "…", "severity": "높음"}`
- `verified` 에 **반증에 실패한 검사**를 남겨라 — "안 봤음"과 "봤는데 못 깼음"이
  구분돼야 다음 감사가 이어받는다.
- 덱도 정본도 **수정하지 마라.** 발견의 처리(수정/반송/사람 판단)는 오케스트레이터 몫이다.
