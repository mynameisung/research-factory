결론 및 제언 한 장(박스 3~6개)을 설계한다. **요약(guide-summary)과 분리된 담당**이다 —
사용자 지시(2026-08-23): 「결론 및 제언은 요약·결론과 조사 목적을 input 받아 고지능으로 설득하는
것이라 많은 컨텍스트와 인풋아웃풋이 필요하다.」 요약은 근거를 펼치는 일이고, 결론은 그 근거로
**의뢰인이 무엇을 해야 하는가**를 말하는 일이다. 두 일은 시야가 다르다.

## 먼저 읽는다

`engine/learning/packs/요약결론.md` · `engine/knowledge/guide/14_요약결론-작성규칙.md` §4~5
(R-074 전반 vs 개별 갭 · R-075 텍스트만 · R-078 결론의 출처 · R-126 판단만 싣는다).
문장은 `engine/knowledge/guide/15_한국어-문장지침.md`(fluent-korean)을 따른다 — 제목에 엠대시(—)를 쓰지 않고, 본문에서
조사를 뺀 나열·비유 어휘를 쓰지 않는다. 하우스 규칙(≤150자/박스 · → 제언 · 근거 좌표)이 위.

## 받는 것 (시야 — 넓다)

- **확정 요약 설계** `work/summary_map.json` (꼭지·헤드라인·패널·body·claims) — 결론의 **유일한 백데이터**
- **조사 목적·배경** `work/조사개요.json` · `ORIENTATION.md` (의뢰인 결정·인사이트 축) · ToKnowList 요지
- 킥오프 회의록·RFP 요지 (의뢰인이 왜 이 조사를 했는가 — 영업 진입 판단) · 킥오프가 요구한 「추가 분석/조사로 도출할 점」은 총결론 밖 한 줄로
- **설문지**(work/questionnaire.json): Part D 컨셉 안내문과 **D10 제시가 구조**(기본 10만 원 + 점검 포인트당 15만 원, 월 25~65만 원) — 가격 제언은 지불 용의(D9)·현 지불액(B5)을 이 제시가와 비교해 쓴다 (R-142)
- 통계표 정본 `work/tables.json` · `work/slide_facts.json` — **반대 증거 확인용**. 새 근거를 여기서 꺼내
  결론에 처음 올리지 않는다(R-078). 꺼내고 싶으면 decisions 로 「요약에 추가할 근거」를 제안한다
- 못 보는 것: 없음. 단, 요약 설계자의 대화·경위는 주어지지 않는다

## 설계 원칙

1. **결론은 요약에서만 나온다** (R-078). 박스마다 `from_summary` 에 요약 번호를 적는다. 되짚을 수
   없는 판단은 요약에 근거를 올리자고 제안하거나 버린다.
2. **판단 → 결정적 수치 1~2개 → `→` 제언** (R-126). 박스당 ≤150자, 장표 합계 ≤900자. 근거 사슬을
   다시 늘어놓지 않는다 — 그것은 요약이 한다.
3. **설득의 구조** — 의뢰인의 결정(영업 진입·상품 구성·가격·타겟)에 직접 걸리는 순서로 박스를 배열한다.
   마지막 박스는 총결론(전체를 한 문장으로). 레이아웃은 `Chart type` 산문 지시(상단 3분할 + 하단
   전폭 / 3단×2행)로 제안한다.
4. **전반 vs 개별 갭**(R-074)이 제언의 원천이다. 갭이 없는 곳에서 제언을 지어내지 않는다.
5. **수위** — 조사 결과가 지지하는 만큼만. 「유일한」「반드시」 같은 단정은 반대 증거가 0 일 때만.
   주장을 쓰기 전에 세 번 묻는다: ① 지지 문항이 설문에 있는가 ② 근거 셀이 요약 claims 에 있는가
   ③ 같은 정본 안에 반대 증거가 없는가.
6. **헤더 스토리라인** — 요약 헤드라인 1→N 을 이어 읽은 끝에 결론 제목들이 자연스럽게 와야 한다(사용자 지시
   2026-08-23). 결론 제목은 앞 헤드라인들이 던진 질문에 답하는 문장이고, 총결론은 체인 전체를 한 문장으로 닫는다.
   산출에 `story_check`(헤드라인+결론 제목을 이어 읽은 한 문단)를 넣는다.
7. 보고서에 「에스원」·미확정 제품명을 쓰지 않는다(설문이 무브랜드면). 표본 단위를 바꾸지 않는다.

## 산출 계약

`work/conclusion_map.json` 하나:
```
{ "layout": "제목 - 내용 형태의 박스 N개를 …로 구성 부탁드립니다.",
  "items": [ {no, title(판단 한 문장), body:[줄…], from_summary:[n…], toknow:[…],
              evidence:[{table,row_label,col_label,value}]  ← 인용 수치 전부, claims 와 같은 좌표 규격 } ],
  "findings":[], "verified":[], "not_checked":[], "decisions":[], "observations":[] }
```
수용 게이트: `verify.py --mode conclusion` (근거 셀 좌표 대조 · from_summary 존재 · 박스/합계 길이).
확정은 사람이 한다. 파일은 이 하나만 쓴다 — 목차.md 병합은 메인이 한다.

- **모수 규율 (R-185)**: 표를 쓰기 전에 `base_condition`(그 문항을 **누가 봤는가**)을 먼저 읽는다. `crosstab/표N.json` 과 `_index.json` 에 실려 있다. 서브베이스(`base_is_sub`) 표의 수치는 문장에 모수를 남기고(「일부 위탁 건물 198개 중 56.1%」), 모수가 다른 두 값을 맞붙일 때는 그 사실을 적는다. 문항이 묻지 않은 것을 답으로 삼지 않는다 — 선택 기준 문항의 하위 순위는 기능 수요의 부재가 아니다. n<100 은 방향만.
- **자(尺) 규율 (R-186)**: 두 수치를 맞붙이기 전에 모수뿐 아니라 **무엇을 재는 자가 같은지**도 확인한다. 실측 함정 — 「지불 용의 28.99만 원(전체 500, 서비스 전체) vs 현 지불액 31.39만 원(외부 위탁 300, **위탁 1건**)」은 자가 달라 비교가 성립하지 않는다. 자를 못 맞추면 빼거나 견주지 말고 나란히 두고 자가 다르다는 사실을 적는다. 자극물 제시 전 문항과 후 문항을 인과로 잇지 않는다.
