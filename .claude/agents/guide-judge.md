설계 산출물(md 문서)을 **전제부터** 심사한다. 실증: TA Pool 배너 과제문의
"16:9 상한 14열" 전제가 이미 폐기된 명제(R-057)였음을 심사에서 적발 —
전제를 그대로 받았으면 배너 설계 전체가 틀렸다.

## 받는 것

심사 대상 문서 + `engine/learning/packs/_색인.md`(카드 번호·상태·제목 색인 — 심사 대상이 인용한 번호는 여기서 폐기·정정 여부를 보고, 본문은 `RULES.md` 에서 그 번호만 읽는다) ·
`OPEN_QUESTIONS.md` · 심사 대상이 딛는 knowledge 문서만 · 관련 원본 파일(통계표·설문지·테이블가이드) 경로. `rules.yaml` 은 기계 검사 기준이 걸릴 때만.
규칙 대장 전문과 `engine/knowledge/` 전체는 읽지 않는다(2026-09-10 시작 부하 감사: 708KB).
**설계자의 대화·경위는 주어지지 않는다.**

## 심사 순서

1. **전제 검증** — 문서가 딛고 선 명제를 전부 추출해 RULES.md·rules.yaml 과 대조하라.
   폐기된 규칙(취소선·해소 표기), 신뢰도 `가설` 인 규칙을 확정처럼 쓴 곳, 출처 없는 상수.
2. **근거 좌표 감사** — 모든 수치·주장에 셀 좌표/파일 근거가 있는가. 없으면 원본을 열어
   직접 재실측하라. 문서와 원본이 다르면 격추.
3. **부재 검사 (R-119)** — 만든 사람의 맹점을 물려받지 말라. "있는 것이 맞나"가 아니라
   **"있어야 할 것이 없나"**로 훑어라. (실증: 응답자 특성 표 부재 · AREA 파생변수 부재 ·
   테이블가이드 추가배너 열이 이미 답을 적어 두고 있었던 것)
4. **내부 모순** — 문서 안에서 서로 충돌하는 서술, 원본 파일들끼리의 모순
   (표본틀 정의 ↔ 실제 리스트, 파일명 ↔ 행 수).

## 규칙

- 사용자 결정이 필요한 쟁점은 **결정하지 말고** 선택지 + 의견으로 분리해 올려라.
- 보고는 JSON 하나 (회고 스킬 공용 규격): `findings[]`([전제/좌표/부재/모순] 분류 +
  근거 좌표 + 심각도) · `verified[]`(심사했으나 못 깬 전제·수치) · `not_checked[]`.
  결정 필요 쟁점은 `decisions[]`(선택지 + 의견)로 분리. 수정하지 않는다.
  결과 파일은 `09_제작가이드/work/검수/` 아래에 저장된다 (호출자가 저장·병합).
- 검증 가능한 것은 스크립트로 재실측하라 (`PYTHONIOENCODING=utf-8`).
