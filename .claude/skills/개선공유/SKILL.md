# 개선공유 — 내 노하우와 개선분을 PR 로

연구원은 git 을 모른다. 이 스킬이 노하우 채집부터 PR 까지 대신한다.
**작업 폴더(working tree)는 절대 바꾸지 않는다** — 커밋은 임시 워크트리에서 만든다.

올라가는 것은 둘이다.
- **노하우 카드** — 쓰다가 얻은 요령. `engine/learning/knowhow/<스킬>.md` 에 카드로 적어 올린다. 규칙보다 가볍다.
- **개선분** — 로컬에서 고친 규칙·지식·도구·스킬 파일.

관리자는 PR 을 받아 **채택**(그대로 병합) · **승격**(규칙 대장·지식·도구로 옮김) · **보류**(사유)를 정한다. 공통으로 쓸 것만 main 에 오르고, 오르면 모두가 `/업그레이드` 로 받는다.

## 절차

1. **선행 확인**
   - `gh auth status` — 로그인이 없으면 `gh auth login --web` 을 안내하고 브라우저 승인까지 기다린다.
   - `git fetch origin` 으로 원격 최신을 받아 둔다.
   - `python report-factory/engine/tools/gen_preamble.py --check` — 스킬의 PREAMBLE 이 원본(`engine/templates/SKILL_PREAMBLE.md`)과
     어긋나면 `gen_preamble.py` 로 채운 뒤 진행한다. 프리앰블은 스킬 파일에서 직접 고친 것을 올리지 않는다.

2. **노하우 채집** — 사용자가 「이 노하우 올리자」고 한 것이 있으면 그것부터. 없으면 조사 메모리에서 후보를 뽑는다.
   - 활성 조사(`projects/.active`)의 `_memory/MEMORY.md`(결정된 것 · 다음 세션이 알아야 할 것) · `사용자입력.jsonl`(최근) · `스킬실행.jsonl`(어느 스킬을 썼나)을 읽는다.
   - 스킬별로 **구체적으로** 묻는다. 「노하우 있나요?」는 아무것도 못 건진다.
     - 웹테스트: 「사이트 선택자를 고쳤나요? 테스트 계정은 어떻게 얻었나요? 손으로 보탠 시나리오가 있나요?」
     - 제작가이드: 「목차·배너에서 손으로 바꾼 것은? 검증기가 잘못 잡은 것은? 제작팀이 되물은 것은?」
     - 보고서작성: 「제작본에서 반복된 실수는? 차트를 고칠 때 막힌 것은? 렌더에서 자주 깨진 장표는?」
   - 후보마다 카드 초안을 보여 주고 고른 것만 `engine/learning/knowhow/<스킬>.md` 끝에 붙인다. 형식은 그 파일 머리에 있다.
     번호는 마지막 번호 다음, 상태는 `제안`, 올린 사람은 `gh api user -q .login`.
   - **규칙 수준**(같은 상황이 오면 반드시 또 고쳐야 하는 것)이면 노하우가 아니라 `/회고` 대상이라고 알리고 카드에는 넣지 않는다.
   - 노하우도 개선분도 없으면 「올릴 것이 없습니다」로 끝낸다.

3. **변경분 수집** — `git status --porcelain` 에서 **공유 대상 경로만** 추린다:
   `report-factory/engine/` · `.claude/skills/` · `.claude/agents/` · `README.md` · `CHANGELOG.md`.
   그 밖의 경로가 잡히면 목록만 보여 주고 PR 에서는 뺀다(조사 데이터 `projects/` 는 어떤 경우에도 올리지 않는다).

4. **안전 게이트** — diff 전체를 훑어 다음이 보이면 **중단하고 보고**한다:
   - API 키 패턴 (`nv-`·`sk-`·`gho_` 등 실제 키 문자열)
   - 조사 원자료를 통째로 붙여 넣은 흔적 (통계표 덤프·설문 전문 등).
     규칙 문서가 근거로 인용하는 개별 수치는 정상이다 — 파일 단위 유입만 막는다.
   - 노하우 카드에 고객사 실명·응답자 정보·계정 정보가 들어갔으면 지우고 다시 쓴다(테스트 계정 요령은 「어디서 받나」까지만).

5. **요약·확인** — 노하우 카드는 제목 목록으로, 개선분은 파일별로 무엇이 왜 바뀌었는지 한국어로 요약해 보여 주고
   (규칙이면 규칙 번호와 요지), **사용자 확인을 받은 뒤** 진행한다.

6. **PR 생성** — 작업 폴더를 건드리지 않도록 임시 워크트리에서:
   ```
   git worktree add <스크래치>/rf-pr origin/main --detach
   (3에서 추린 파일들을 워크트리로 복사 · 삭제분은 워크트리에서도 삭제)
   git -C <워크트리> checkout -b 개선/<gh 계정명>-<YYMMDD>
   git -C <워크트리> add -A → commit (요약을 커밋 메시지로)
   git -C <워크트리> push -u origin <브랜치>
   gh pr create --base main --title "<한 줄 요지>" --body "<무엇을·왜 + 검증 여부>"
   git worktree remove <워크트리> --force
   ```
   같은 날 두 번째 실행이면 브랜치명에 `-2` 를 붙인다. 노하우만 있으면 제목 앞에 `[노하우]`, 개선분이 섞이면 `[노하우+개선]`.
   PR 본문에는 카드 제목 목록과 「관리자 판정 요청: 채택 / 승격 / 보류」 한 줄을 넣는다.

7. **보고** — PR URL 을 알려 주고, 「관리자가 병합하면 `/업그레이드` 로 받게 된다」고
   안내한다. 로컬 수정은 그대로 남아 있으므로 지금 하던 작업은 계속해도 된다고 덧붙인다.

## 관리자가 PR 을 받으면 (관리자 세션에서)

- **채택** — 카드 상태를 `채택` 으로 바꾸고 병합한다. 그 스킬을 쓰는 모두가 시작할 때 읽게 된다.
- **승격** — 규칙 수준이면 `/회고` 절차로 RULES.md 카드를 만들고(요지 줄 포함) 노하우 카드 상태를 `승격 → R-nnn` 으로. 도구로 박을 것(선택자 프로필·검증기 검사)이면 코드에 반영하고 `승격 → <도구>`.
- **보류** — 상태를 `보류(사유)` 로 바꿔 병합한다. 카드는 지우지 않는다. 같은 요령이 다시 올라오면 그때 다시 본다.
- 병합할 때 `VERSION` 과 `CHANGELOG.md` 를 함께 올린다. CHANGELOG 한 줄이 연구원 화면의 「바뀐 점」이다.

## 주의

- 커밋 메시지·PR 본문은 연구원 언어로 쓴다. 근거(어느 조사에서 왜 바뀌었나)를 한 줄이라도 남긴다.
- 병합 여부는 관리자 몫이다 — PR 이 올라갔다고 규칙이 확정된 것이 아니라고 알려 준다.
