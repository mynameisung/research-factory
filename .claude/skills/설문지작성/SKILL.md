## PREAMBLE — 본 절차보다 먼저 실행한다

```bash
python "$(git rev-parse --show-toplevel)/report-factory/engine/tools/preamble.py" --skill 설문지작성 <조사 폴더 인자가 있으면 그대로>
```

한 번의 호출이 새 판 확인·활성 조사 지정·조사 메모리 위치·실행 기록을 처리하고 `KEY: 값` 줄로 답한다. 줄마다 이렇게 한다.

- **`UPDATE: NONE`** 또는 **`DISABLED`** — 아무 말 없이 본 절차로 간다.
- **`UPDATE: UPGRADE_AVAILABLE <내판> <새판>`** — 먼저 `update_check.py whats-new <새판>` 으로 바뀐 점을 읽는다.
  `update_check.py config get auto_upgrade` 가 `true` 면 묻지 않고 `/업그레이드` 를 실행한 뒤 본 절차로 간다.
  아니면 AskUserQuestion 으로 묻는다 — 「report-factory **<새판>** 이 나왔습니다 (지금 <내판>). <바뀐 점 한 줄>. 올릴까요?」
  1. **지금 올린다** → `/업그레이드` → 본 절차
  2. **앞으로는 자동으로** → `update_check.py config set auto_upgrade true` → `/업그레이드` → 본 절차
  3. **지금 말고 나중에** → `update_check.py snooze <새판>`. 출력의 next 값대로 「다음 알림은 24시간 뒤입니다」라고 알린다(두 번째는 48시간, 세 번째부터 1주일) → 본 절차
  4. **다시 묻지 않는다** → `update_check.py config set update_check false`. 「다시 켜려면 `config set update_check true`」 → 본 절차
- **`UPDATE: JUST_UPGRADED <이전판> <내판>`** — `whats-new <내판>` 을 읽어 「<내판> 으로 올라왔습니다: <바뀐 점>」 한 줄만 말하고 본 절차로 간다.
- **`UPDATE: CHECK_FAILED <이유>`** — 「판을 확인하지 못했습니다(<이유>). 그대로 진행합니다」 한 줄만 말하고 본 절차로 간다. 최신으로 읽지 않는다.
- **`MEMORY: <경로>`** — 그 `MEMORY.md` 를 읽는다. 「결정된 것」은 다시 묻지 않는다. 스킬이 끝날 때 세 절(결정된 것 · 지시의 요지 · 다음 세션이 알아야 할 것)을 갱신한다. `MEMORY_NEW: yes` 면 읽을 것이 없으니 끝날 때 채우기만 한다.
- **`MEMORY: NONE`** — 조사 폴더 인자가 없었다. 조사가 정해지는 즉시 조사 폴더를 인자로 이 명령을 다시 실행한다.
- **`PATHS: {…}`** — 역할 → 경로 JSON. 설문지·통계표·정본 JSON·제작본·최종보고서 같은 파일과 단계 폴더를 **여기서 찾는다.** 폴더 이름을 추측하거나 `input/` 을 뒤지지 않는다. 역할 하나만 필요하면 `paths.py <조사> --role <역할>`. `LAYOUT: v1` 이면 옛 배치이고 같은 역할 이름으로 풀려 있으니 그대로 쓴다(`paths.py migrate` 는 사람이 정한다). `LAYOUT: none` 이면 `paths.py new <프로젝트>/<조사>` 로 뼈대를 만든다. `files_all` 에 설문지나 통계표가 여러 벌 있으면 어느 것을 쓸지 사용자에게 확인한다.
- **`TRACKING: …`** 이 있으면 트래킹 조사다. `PREV_PATHS:` 의 이전 회차 통계표·최종보고서·제작가이드를 전차 비교의 정본으로 쓴다(전년 수치를 기억이나 추정으로 쓰지 않는다). 이전 회차가 `NONE` 이면 첫 회차이므로 비교 없이 간다.

사용자 입력과 손 편집은 훅이 같은 `_memory/` 폴더에 자동으로 남긴다(`knowledge/02_프로젝트-메모리.md`). 이 블록은 스킬 본문의 어떤 규칙보다 먼저다.

TKL(받은 경우만) → **구조화 엑셀** → **설문지** 의 두 번째 화살표를 맡는다. 구조화는 연구원이 이미 만들었다.
이 스킬은 그것을 온라인실사팀이 그대로 구축할 수 있는 엠브레인 양식 설문지로 옮긴다.

```
구조화.xlsx ──read_structure──▶ structure.md ──(Claude)──▶ 설문명세.json ──build_questionnaire──▶ 설문지.docx
                                                            check_questionnaire (구조화 누락 · 로직 · 파서 왕복)
                                                            questionnaire-adversary (문장 · 보기 · 흐름 반증)
```

인자: 조사 폴더와 구조화 파일. 예 `/설문지작성 projects/2026_○○_만족도/01_본조사 구조화.xlsx`
구조화 파일만 받고 조사 폴더가 없으면 `paths.py new <연도_클라이언트_프로젝트>/01_<조사약칭>` 으로 뼈대를 만들고 파일을 `03_설문지/` 에 넣는다.

## 이 업무의 헌법 3

1. **구조화가 정본이다.** 구조화에 있는 문항은 전부 설문지에 간다. 빼면 `meta.skipped_src` 에 사유와 함께 적는다.
   구조화에 없는 문항을 넣으면(`src` 없음) 이유를 변환 메모에 적는다. 조용히 더하거나 빼지 않는다.
2. **도구는 서식만, 문장은 Claude 가, 결정은 사람이.** 문장·보기·로직은 `knowledge/50_설문지-작성.md` 의 하우스 규칙으로 짓는다.
   구조화에 없는 보기를 새로 지었거나, 범위·조건을 추론했으면 그 문항에 `review` 를 달아 **노란 번호**로 드러낸다.
   담당자 연락처·사례품 금액·쿼터 수치·조사 기간은 지어내지 않고 묻는다.
3. **실사팀이 그대로 구축할 수 있어야 한다.** 모든 분기는 문항 코드로 쓴 `[BASE:]` · `[PROG:]` 로 남기고,
   산출 .docx 는 `parse_questionnaire.py` 로 다시 읽혀야 한다(→ `/웹테스트` · `/제작가이드` 가 이 파서를 쓴다). 치명 0 이 수용 조건.

## Step 0 — 준비와 오리엔테이션

```bash
ROOT="$(git rev-parse --show-toplevel)"; T="$ROOT/report-factory/engine/tools"
W="<조사>/03_설문지/work"; mkdir -p "$W"
```

경로는 `C:/Users/…` 꼴이나 리포 기준 상대 경로로 넘긴다. Git Bash 의 `/c/Users/…` 는 파이썬(python-docx)이 못 연다.

AskUserQuestion 한 번으로 **구조화에 없는 것만** 묻는다(이미 `MEMORY.md` 「결정된 것」에 있으면 묻지 않는다).
- 표지 형태 — 기본(조사 대상자·방법·샘플 수·쿼터) / 인사말 박스 포함(공공·기관 조사, 응답자가 표지를 봄 → 담당자·연락처 필요)
- 끝맺음 — 사례품 있음(금액) / 없음 / 실사팀 기본 종료 화면
- 응답자 호칭 — 귀하 / 귀사 / 귀 건물 (구조화 문장에서 분명하면 묻지 않는다)
- 구조화에서 뜻이 불분명한 것(셀 색·빨간 행·충돌하는 응답대상)이 보이면 같은 질문 묶음에 넣는다

## Step 1 — 구조화 펼치기

```bash
python "$T/read_structure.py" "<구조화.xlsx>" "$W"
```

`$W/structure.md` 를 **처음부터 끝까지** 읽는다. 구조화 시트뿐 아니라 참고 시트(메일 본문 · 이전 버전 · 설문지 초안 · To-know list · 응답보기)와
곁표·안내 띠·셀 색·열 밖 메모까지 본다. 참고 시트의 고객 요청이 구조화 본표에 반영돼 있지 않으면 목록으로 적어 둔다(Step 4 에서 보고).
열 역할이 `?` 로 나온 열은 머리말을 보고 뜻을 정한다.

## Step 2 — 설문명세 쓰기

`$W/설문명세.json` 을 쓴다. 형식은 지식 문서 4절, 예시는 fixture. 순서:

1. **파트 체계** — 구조화 대분류를 `SQ` · `A` · `B` … · `DQ` 로 대응시키고 흐름(3-1)을 확인한다. 파트 제목은 구조화 대분류 이름을 살린다.
2. **문항마다** — 구조화 행 순서대로 쓰되, 3-1 흐름 규칙(전반 평가는 속성 평가 뒤 등)에 어긋나는 행만 옮기고 `meta.notes` 에 적는다.
   - `src` 에 구조화 행 `ref` 를 단다. 한 행이 여러 문항이 되거나(서비스별 반복) 여러 행이 한 문항(행렬)이 되어도 모두 단다.
   - `kind` 를 2절 변환표로 정한다. 척도는 오름차순 프리셋. 리스트·드롭다운·지도 선택은 `list`, 응답자 분류 같은 참고 표는 `table`.
   - 문장: 구조화 문장이 있으면 **뜻을 바꾸지 않고** 하우스 문형으로 다듬는다(합쇼체 · 기준 시점 · 지시문 · 굵게 1~2곳).
     구조화에 주제만 있으면(`주거시설` · `추천 의향`) 같은 파트의 이웃 문항 문형에 맞춰 짓는다.
   - 보기: 구조화 원안을 그대로 쓰되 번호·기타·없음·구간 경계만 하우스 규칙으로 정리한다. 원안이 없으면 참고 시트에서 찾고,
     그래도 없으면 짓고 `review` 를 단다. 짝 문항(만족/불만족 이유)은 대칭으로.
   - 로직: 응답대상·응답 로직·비고를 `base` · `prog` · `range` · `terminate` · `quota` 로 옮긴다. `불만족` 후속은 `=1~3`.
     `이용경험자 대상` 은 그 경험을 묻는 SQ 문항을 가리키게 하고, 없으면 SQ 문항을 만든다(`src` 없음 + 메모).
   - 로테이션: 명목형 보기 5개 이상이면 `rotation` 을 반드시 정한다. 순서형이면 `ordinal: true`.
   - 구성·응답대상이 빈 행, 참고 시트끼리 충돌하는 보기는 지식 문서 1절의 우선순위대로 정하고 `review` 를 단다.
3. **표지·끝맺음** — Step 0 의 답으로 `meta.cover` · `meta.greeting`(지식 문서 3-7 틀) · `meta.closing`. 모르는 연락처·금액은 `==…==` 노란 형광 자리로 비운다.
4. **변환 메모** — `meta.notes` 에 사람이 알아야 할 결정(번호를 바꾼 곳 · 뒤집은 척도 · 반영하지 않은 행과 사유 · 참고 시트에서 가져온 보기 · 참고 시트 요청 중 미반영).

문항이 60개를 넘으면 파트별로 나눠 쓰되, 보기 목록이 여러 문항에서 반복되면(브랜드 목록 · 경로 목록) **한 번 정한 문구를 복사**해 쓴다.

## Step 3 — 서식 입히기와 기계 검수

```bash
python "$T/build_questionnaire.py" "$W/설문명세.json" "<조사>/03_설문지/<조사약칭>_설문지_<YYMMDD>.docx"
python "$T/check_questionnaire.py" "$W/설문명세.json" --structure "$W/structure.json" \
       --docx "<조사>/03_설문지/<조사약칭>_설문지_<YYMMDD>.docx" --out "$W/검수.json" --md "$W/검수.md"
```

- **치명**(Q-01 번호 · Q-03 참조 · Q-04 BASE 코드 범위 · Q-05 필수 요소 · Q-14 파서 왕복)은 명세를 고쳐 0 으로 만든다.
- **경고**는 하나씩 판단한다. Q-11(구조화 누락)은 반영하거나 `skipped_src` 로 사유를 남긴다. Q-10(로테이션)은 결정해 명시한다.
  고치지 않기로 한 경고는 `meta.notes` 에 이유를 적는다.
- 파일 이름은 README 규칙 `<구분자>_<내용>_<일자>`. 같은 날 다시 만들면 `_v2`.

## Step 4 — 반증 검토

`questionnaire-adversary` 에이전트를 띄운다(백그라운드 아님 — 결과를 받아 고친다). 주는 것: `structure.md` 경로 · `설문명세.json` 경로 ·
산출 .docx 경로 · TKL 경로(있으면) · 조사 목적 한 줄. **내가 왜 그렇게 썼는지는 주지 않는다.**
돌아온 findings 중 맞는 것은 명세에 반영하고 Step 3 을 다시 돈다. 판단이 갈리는 것은 사람에게 넘길 목록에 넣는다.

## Step 5 — 보고

1. 산출 .docx 를 PDF 로 렌더해(가능하면 Word COM, 아니면 LibreOffice) 첫 두 쪽을 눈으로 확인한 뒤 SendUserFile 로 .docx 를 보낸다.
2. 채팅에 요약한다 — 파트·문항 수 · 검수 결과(치명 0 · 경고 n) · **확인 필요(노란 번호) 목록** · 변환 메모 · 참고 시트 요청 중 미반영 ·
   사람이 정할 것(연락처·사례품·쿼터 수치 등 비워 둔 것).
3. `_memory/MEMORY.md` 갱신 — 결정된 것(표지 형태 · 호칭 · 사례품 · 척도 방향 · 번호 체계) · 다음 세션이 알아야 할 것(남은 확인 사항).
4. 다음 단계 안내 — 연구원 검토 → 고객 송부 → 확정본을 `03_설문지/` 에 두면 온라인실사팀 구축 → `/웹테스트`.

## 수정 요청이 오면

연구원·고객 피드백은 **명세를 고쳐 다시 빌드**한다(.docx 를 직접 고치지 않는다 — 다음 수정 때 덮인다). 고객이 .docx 에 직접 메모·수정해
돌려보냈으면 `python "$T/parse_questionnaire.py" <고객본.docx> "$W/고객본.json"` 으로 읽고 명세와 대조해 차이를 명세에 옮긴 뒤 다시 빌드한다. 고친 내역은 `meta.notes` 에 날짜와 함께 남긴다.
