# 웹테스트 (업무 C)

연구원이 브라우저에서 「다음 → 다음 → …」 하며 눈으로 보던 실사 검수를 기계가 대신 걷게 한다.
사람이 하는 일은 **로그인**과 **판정**이고, 순회와 대조는 도구가 한다.

```
설문지 정본 ──▶ 시나리오 행렬 ──▶ 브라우저 순회 덤프 ──▶ 정본 대조 ──▶ 수정요청서(.xlsx)
questionnaire.json   시나리오.json      덤프_<ID>.json        findings.json    대조요약.md
```

인자: 조사 폴더 경로와 실사 URL. 예 `/웹테스트 projects/2026_KB손보_자동차CSI/01_본조사 https://isurvey.panel.co.kr/…`

---

## 판 확인과 조사 메모리 — 본 절차보다 먼저

report-factory 는 GitHub 정본(FineHourTeam/report-factory)에서 갱신된다. 작업 폴더를 건드리지
않고 원격의 `VERSION` 한 줄만 읽어(`git fetch`, pull 아님) 새 판이 있는지 본다.

```bash
python "$(git rev-parse --show-toplevel)/report-factory/engine/tools/update_check.py"
```

- **출력이 없으면** 최신이다. 아무 말 없이 본 절차로 간다.
- **`UPGRADE_AVAILABLE <내판> <새판>`** 이면 먼저 같은 스크립트에 `whats-new <새판>` 을 주어 바뀐 점을 읽는다.
  `config get auto_upgrade` 가 `true` 면 묻지 않고 `/업그레이드` 를 실행한 뒤 본 절차로 간다.
  아니면 AskUserQuestion 으로 묻는다 — 「report-factory **<새판>** 이 나왔습니다 (지금 <내판>). <바뀐 점 한 줄>. 올릴까요?」
  1. **지금 올린다** → `/업그레이드` 실행 → 본 절차
  2. **앞으로는 자동으로** → `config set auto_upgrade true` → `/업그레이드` → 본 절차
  3. **지금 말고 나중에** → `snooze <새판>` 실행. 출력의 next 값대로 「다음 알림은 24시간 뒤입니다」라고 알린다(두 번째는 48시간, 세 번째부터 1주일) → 본 절차
  4. **다시 묻지 않는다** → `config set update_check false`. 「다시 켜려면 `config set update_check true`」 → 본 절차
- **`JUST_UPGRADED <이전판> <내판>`** 이면 `whats-new <내판>` 을 읽어 「<내판> 으로 올라왔습니다: <바뀐 점>」 한 줄만 말하고 본 절차로 간다.
- **`CHECK_FAILED …`** 면 「판을 확인하지 못했습니다(<이유>). 그대로 진행합니다」 한 줄만 말하고 본 절차로 간다. 이것을 최신으로 읽지 않는다.

그다음 **조사 메모리**를 연다. 조사 폴더 인자를 받았으면 `python "$(git rev-parse --show-toplevel)/report-factory/engine/tools/capture_prompt.py" set-active <프로젝트>/<조사>` 로 활성 조사를 적고, `report-factory/projects/<프로젝트>/<조사>/_memory/MEMORY.md` 를 읽는다. 「결정된 것」은 다시 묻지 않는다. 스킬이 끝날 때 MEMORY.md 의 세 절(결정된 것 · 지시의 요지 · 다음 세션이 알아야 할 것)을 갱신한다. 사용자 입력과 손 편집은 훅이 같은 폴더에 자동으로 남긴다(`knowledge/02_프로젝트-메모리.md`).

이 블록은 네 스킬(제작가이드·보고서작성·회고·웹테스트)에 같은 내용으로 들어 있다. 고칠 때는 넷을 함께 고친다.

## 이 업무의 헌법 3

1. **로그인은 사람이 한다.** 실사 사이트는 엠브레인 패널 계정이 필요하다. 스킬은 아이디·비밀번호를 받지도, 넣지도 않는다.
   브라우저를 띄워 주고 기다렸다가, 사람이 첫 문항 화면까지 들어오면 그때부터 걷는다. 세션은 `work/auth.json` 에 저장해 다음 순회에 다시 쓴다(조사 폴더 밖으로 내보내지 않는다).
2. **정본은 설문지다.** 웹 화면이 설문지와 다르면 웹이 틀린 것으로 적는다. 설문지가 낡았다고 판단되면 고치지 말고 「정본 확인」으로 분류해 사람에게 넘긴다.
3. **기계가 못 본 것은 못 봤다고 적는다.** 보기 카드 이미지 내용, 로테이션의 무작위성, 디자인, RANGE 경계값, 복수 응답 상한은 도구가 판정하지 않는다. 마지막 절의 「사람 검수 목록」으로 남긴다.

- 조사 폴더의 `_memory/MEMORY.md`
- 설문지 정본이 이미 있으면 `1_제작가이드/work/questionnaire.json` (없으면 Step 1 에서 만든다)

## Step 0 — 준비

```bash
ROOT="$(git rev-parse --show-toplevel)"; T="$ROOT/report-factory/engine/tools"
python -c "import playwright" 2>/dev/null || (python -m pip install -q playwright && python -m playwright install chromium)
mkdir -p "<조사>/3_웹테스트/in" "<조사>/3_웹테스트/work" "<조사>/3_웹테스트/out"
```

Playwright 와 Chromium 은 설치에 몇 분 걸린다. 처음이면 사용자에게 한 줄 알린다. 설문지 `.docx` 는 `3_웹테스트/in/` 에 둔다.

## Step 1 — 설문지 정본

```bash
python "$T/parse_questionnaire.py" "<조사>/3_웹테스트/in/<설문지>.docx" "<조사>/3_웹테스트/work/questionnaire.json"
```

`1_제작가이드/work/questionnaire.json` 이 이미 있고 설문지 판이 같으면 그것을 복사해 쓴다.
파서 요약에서 문항 수·`[BASE:]`·`[RANGE:]`·조사 중단 보기 수를 사용자에게 한 줄로 보인다. 설문지 양식이 고객사마다 달라 파서가 놓치는 것이 있다(코드 `A2- b.` 같은 변형). 놓친 문항은 사용자에게 묻지 말고 JSON 을 손으로 보태고 `_memory/MEMORY.md` 에 적는다.

## Step 2 — 시나리오 행렬

```bash
python "$T/webtest_scenarios.py" "<조사>/3_웹테스트/work/questionnaire.json" "<조사>/3_웹테스트/work"
```

`시나리오_매트릭스.md` 를 사용자에게 보인다(행 = 문항, 열 = 시나리오, — = 노출되면 안 됨, ■ = 조사 중단).

- **S0** 기본 경로(가장 많은 문항이 보이는 답) 하나, **B_** 분기 경로(S0 에서 숨은 반대쪽 분기를 밟는다), **T_** 조사 중단 보기마다 하나, **H_** 노출 조건마다 하나가 자동으로 생긴다. 실측: 비상주 58문항 → 21개, TA 17문항 → 5개.
- 출력에 「못 읽은 노출 조건」이나 「어느 시나리오도 밟지 못한 문항」이 있으면 그 문항은 사람이 답을 정해야 한다(숫자 입력 문항의 항목값으로 갈리는 조건이 대표적이다). 사용자에게 「이 문항은 어떤 답일 때 보이나요?」 를 문항별로 묻고 `시나리오.json` 의 `answers` 를 고친다.
- 연구원이 늘 쓰던 시나리오(예: 남성·서울·20대·자동차보험 가입)가 있으면 그것을 S1 으로 추가한다. 시나리오는 `answers{문항: {choose:[…]|text:"…"}}` 만 적으면 되고 `expect` 는 다시 생성하지 않아도 된다(대조기는 `expect` 가 없으면 S0 의 것을 쓴다 — 노출 조건이 다르면 새로 만든다).

## Step 3 — 첫 순회 (로그인 · 선택자 맞추기)

```bash
python "$T/webtest_walk.py" "<URL>" "<조사>/3_웹테스트/work/시나리오.json" "<조사>/3_웹테스트/work" \
  --scenario S0 --profile isurvey --headed --login-wait 120 --save-state "<조사>/3_웹테스트/work/auth.json" --save-html 3 --screenshots
```

브라우저가 뜨면 사용자에게 「로그인하고 첫 문항 화면까지 들어가 주세요. 120초 뒤 순회를 시작합니다」 라고 말한다.
순회 로그는 페이지마다 `p001 SQ1 보기 3 입력 0 → 다음` 꼴이다. 다음 세 가지를 본다.

| 증상 | 원인 | 조치 |
|---|---|---|
| `다음 버튼을 찾지 못함` | 사이트의 버튼 선택자가 프로필과 다름 | `html_S0_p001.html` 을 열어 버튼 요소를 찾고 `webtest_walk.py` `PROFILES["isurvey"]["next"]` 맨 앞에 추가 |
| `화면이 바뀌지 않음` | 필수 응답 미충족(선택이 안 들어감) 또는 라디오가 이미지 버튼 | 캡처 `캡처_S0/p00N.png` 확인 → 선택자 조정 |
| `code_guess` 가 비어 있음 | 문번호가 화면에 없거나 형식이 다름(예 「문 1.」) | 대조기가 문장 유사도로 짝짓는다. 유사도 짝짓기가 자주 틀리면 `RE_CODE` 를 사이트 형식에 맞춘다 |

프로필을 고쳤으면 그 자리에서 `/개선공유` 대상으로 메모한다. 같은 엔진(isurvey)이면 다음 조사에서 그대로 쓴다.

**주의 — 응답 1회 제한.** 실사 사이트는 한 계정이 한 번만 응답하게 막는 경우가 있다. 두 번째 순회부터 「이미 참여하셨습니다」 로 끝나면 테스트 모드 URL 이나 테스트 계정 여부를 사용자에게 묻는다. 스킬이 우회하지 않는다.

## Step 4 — 나머지 시나리오 순회

```bash
python "$T/webtest_walk.py" "<URL>" "<조사>/3_웹테스트/work/시나리오.json" "<조사>/3_웹테스트/work" \
  --scenario all --profile isurvey --storage-state "<조사>/3_웹테스트/work/auth.json" --screenshots
```

시나리오마다 `덤프_<ID>.json` 과 `캡처_<ID>/` 가 남는다. 하나가 중간에 끊기면(`끝:` 줄을 본다) 그 시나리오만 `--scenario <ID>` 로 다시 돈다. 뒤로가기가 안 되는 엔진이므로 재순회는 늘 처음부터다.

## Step 5 — 정본 대조 → 수정요청서

```bash
python "$T/webtest_compare.py" "<조사>/3_웹테스트/work/questionnaire.json" "<조사>/3_웹테스트/work/시나리오.json" "<조사>/3_웹테스트/out" "<조사>/3_웹테스트/work/덤프_"*.json
```

`대조요약.md` 를 읽고 사용자에게 **치명부터** 보인다.

| 심각도 | 종류 | 뜻 |
|---|---|---|
| 치명 | QUESTION_MISSING · QUESTION_UNEXPECTED · TERMINATE_MISMATCH · PIPING_MISSING | 문항이 안 나옴 · 안 나와야 할 문항이 나옴 · 이탈이 안 됨 · 파이핑이 안 됨 |
| 경고 | OPTION_MISSING · OPTION_EXTRA · TEXT_MISMATCH | 보기 누락 · 보기 추가 · 문구 다름(오탈자·수정 미반영) |
| 참고 | OPTION_ORDER · UNMATCHED_PAGE | 보기 순서 다름(로테이션이면 정상) · 정본에 없는 페이지(안내 페이지·연습 문항이면 정상) |

사람이 판정할 것을 골라 준다. 로테이션 지시가 있는 문항의 OPTION_ORDER, 안내 페이지의 UNMATCHED_PAGE, 설문지 쪽이 낡은 TEXT_MISMATCH 는 사용자가 「정상」이라 하면 `findings.json` 에서 지우고 다시 `webtest_compare.py` 를 돌리지 않는다 — 수정요청서 `.xlsx` 에서 그 행을 지운다(수정요청서는 사람의 문서다).

`수정요청서_<날짜>.xlsx` 열: No · 시나리오 · 문항 · 구분 · 심각도 · 현상 · 요청 · 페이지. 같은 결함이 여러 시나리오에서 잡히면 한 줄로 합쳐져 있다.

## Step 6 — 마무리와 재테스트

1. 수정요청서를 개발 담당자에게 보내는 것은 사람이 한다. 스킬은 파일 경로만 준다.
2. 수정본이 올라오면 **같은 `시나리오.json` 으로 Step 4 → 5 를 다시** 돈다. 지적 건수가 0 이 될 때까지가 검수다.
3. `_memory/MEMORY.md` 갱신: 결정된 것(테스트 계정·URL·프로필 수정) · 지시의 요지 · 다음 세션이 알아야 할 것(남은 지적, 사람 검수 목록 결과).
4. 고객사 추가 문항이 들어오면 설문지 정본을 먼저 고치고(Step 1) 시나리오를 다시 뽑는다(Step 2). 설문지를 안 고치고 웹만 보면 정본이 둘이 된다.

## 사람 검수 목록 (기계가 판정하지 않는 것)

순회가 끝나면 이 목록을 사용자에게 그대로 넘긴다. 캡처(`캡처_<ID>/`)를 보면서 확인한다.

- 보기 카드 **이미지 내용** — 덤프에는 `images[].src/alt` 만 남는다. 어떤 카드가 어느 응답에 나와야 하는지는 설문지 별첨(PPT)과 캡처를 나란히 본다.
- 보기 **로테이션** — 순서가 다르다는 것만 잡는다. 무작위인지, 고정 보기(「기타」·「없음」)가 끝에 남는지는 두 번 이상 돌려 비교한다.
- **RANGE 경계값** — 순회기는 허용 범위의 최솟값만 넣는다. 범위 밖 값이 막히는지는 손으로 한 번 넣어 본다.
- **복수 응답 상한**(최대 3개 등)과 배타 보기(「없음」 선택 시 나머지 해제).
- 진행률 표시 · 디자인 · 모바일 화면.
