# 설문 통계표(Table) 검수

DP실에서 테이블을 수령했을 때 연구원이 손으로 하던 체크리스트를 자동화한다.
**설문지(정답) × 테이블가이드(의도) × 테이블(결과)** 를 3자 대조해 이상 항목을 찾고,
검수한 범위까지 함께 담은 엑셀 리포트를 낸다.

## 핵심 원칙

**1. 눈으로 훑지 마라. 구조화한 뒤 코드로 대조하라.**
100문항 × 배너 30열이면 셀이 수만 개다. 사람 눈으로도, LLM 눈으로도 다 못 본다.
테이블을 먼저 블록 단위 JSON으로 덤프하고(`scripts/dump_tables.py`), 대조는 규칙으로 돌린다.
LLM의 판단은 앞뒤에만 넣는다 — 앞에서 설문지를 읽어 명세를 만들고, 뒤에서 경보를 리뷰한다.

**2. 정답의 출처는 설문지다.**
가이드와 테이블이 서로 일치해도, 설문지와 다르면 이상이다.
가이드가 설문지를 잘못 옮긴 경우가 실제로 흔하다. 항상 설문지를 기준선으로 잡는다.

**3. Base는 숫자가 아니라 정의를 맞춘다.**
"N=412"가 맞는지보다 **"이 문항의 base가 무엇이어야 하는가"** 가 먼저다.
설문지의 base 지시문·prog 로직에서 기대 base를 문장으로 먼저 쓰고,
그 다음 앞 문항 테이블에서 기대 사례수를 산출해 테이블 N과 맞춘다.
정의가 맞는데 숫자가 다르면 그게 진짜 이슈다.

**4. 응답값이 0이라 빠진 보기는 이슈가 아니다. 단, 반드시 목록에 남긴다.**
사용자가 명시한 규칙이다. `07_미출력보기` 시트에 "0건이라 미출력"으로 따로 적고
이슈 목록에는 올리지 않는다. 다만 **0건이 나올 수 없는 보기**(필수 단수문항의 보기 전체가
0인 경우, 쿼터 셀이 0인 경우)는 이슈다.

**5. 확인 못 한 것을 확인한 것처럼 쓰지 마라.**
가중치 적용 여부, 원자료 대비 집계 정확성, 오픈 코딩 품질처럼 테이블만으로 검증
불가능한 항목이 있다. `08_검증범위` 시트에 "검증함 / 검증하지 못함"을 분리해 명시한다.

**6. 경보를 그대로 보고하지 마라.**
파싱 실패로 생긴 오탐이 반드시 섞인다. 원시 경보 → 유형별 묶기 → 표본 재확인 →
확정 이슈. 제외한 건수와 사유도 리포트에 남긴다.

## 진행 순서

### Phase 0 — 입력 확인

받는 것 (3종 세트):

| 파일 | 역할 | 흔한 포맷 |
|---|---|---|
| **설문지** | 정답 — 문항·보기·코드·base/prog 로직·쿼터 | `.docx` (구형 `.doc`·`.hwp`는 변환 요청) |
| **테이블가이드** | 의도 — 행·열(배너) 구조, 넷팅, 통계처리 | `.xlsx` / `.docx` |
| **테이블** | 결과 — 실제 산출된 집계표 | `.xlsx` / `.xls` (구형 `.xls`도 그대로 읽는다) |

**조사 개요는 테이블가이드(DP가이드)에서 읽는다. 사용자에게 먼저 묻지 않는다.**
가이드 앞부분(개요·표지 시트)에 대개 다음이 적혀 있다:

- **총 표본수** — 전체 N. 쿼터 판정과 전 문항 base 검증의 기준선
- **가중치 적용 여부** — 적용이면 가중 변수와, 사례수/가중사례수 중 무엇을 base로 볼지
- **조사 대상·조사 방법** — 쿼터 축이 무엇인지 판단하는 근거
- **차수·비교 테이블 여부** — 전년 대비·Wave 비교면 열 구조가 달라진다

읽은 값은 `guide.json`의 `meta`에 넣고, **어디서 읽었는지(시트·셀 위치)를 함께 적는다.**
리포트 `00_검수요약`의 프로젝트 정보가 그대로 여기서 나온다.

가이드에 없는 항목만 사용자에게 묻는다. 추정해서 채우지 않는다.

**여기서 이미 이슈가 나올 수 있다** — 가이드에 적힌 총 표본수와 테이블의 전체 N이
다르면 그 자체가 **치명** 이슈다. Phase 4를 기다리지 말고 바로 잡는다.

`.hwp`나 구형 `.doc`가 오면 변환을 요청한다. 추측해서 읽지 않는다.
`.xls`는 그대로 읽는다 — 자세한 건 `references/parsing.md`.

### Phase 1 — 설문지 → 명세(`spec.json`)

**정규식 파서를 만들지 마라.** 설문지 포맷은 연구원마다 다르다. 직접 읽고 쓴다.

```bash
python scripts/read_docx.py <설문지.docx> > q_raw.txt
```

문단·표뿐 아니라 **글자색·취소선·형광펜까지** 런 단위로 나온다.
base 조건과 prog 로직은 색이나 대괄호로 표기돼 있는 경우가 많으니 반드시 본다.

문항마다 뽑는다:
- 문번(`Q1`, `SQ2-1`, `A3` …), 문항 문구, 응답유형(단수/복수/순위/척도/숫자/오픈)
- **보기 코드와 문구 전체** — 코드값(1,2,3…)과 라벨을 쌍으로. 기타/없음/모름 포함
- **base 지시문** — "SQ1에서 1번 응답자만", "Q5에서 3번 이상 선택한 자"
- **prog 로직** — 스킵·이탈·표시조건·배타·최소/최대 선택 수
- **쿼터** — 성/연령/지역별 할당 표

스키마는 `references/spec-schema.md`를 따른다.
설문지에 로직이 안 적혀 있으면 "명시 없음"으로 기록하고 Phase 4에서 실측값으로 되돌려 묻는다.

### Phase 2 — 테이블가이드 → 구조 명세(`guide.json`)

가이드에서 뽑는다:
- **조사 개요** — Phase 0에서 읽은 총 표본수·가중치·조사 대상 (`meta`)
- 표 번호(문번) 순서와 **표 제목**
- **행(Row) 구성** — 보기 목록, 넷팅(TOP2/BOTTOM2/긍정·부정), 평균·표준편차 행
- **열(Column, 배너) 구성** — 배너 그룹과 각 셀의 정의
- **Base 표기** — 각 표의 base 문구
- **통계처리 지시** — 백분율 기준, 소수점, 유의차 검정 표기

가이드에 없는데 테이블에 있는 표, 반대의 경우 둘 다 잡아야 하므로 **순서를 그대로 보존**한다.

### Phase 3 — 테이블 → 블록 덤프

```bash
python scripts/dump_tables.py <테이블.xlsx> --list          # 블록 목록(문번/제목/N/행수)
python scripts/dump_tables.py <테이블.xlsx> --block 12      # 12번 블록 원본 격자
python scripts/dump_tables.py <테이블.xlsx> --json > tables.json
```

블록 분할은 휴리스틱이다. **반드시 `--list` 결과를 먼저 훑고, 블록 2~3개를 `--block`으로
열어 실제 표와 맞는지 확인한 뒤** 대조로 넘어간다. 분할이 틀렸으면 `--sep-rows`,
`--title-regex`를 조정한다. 자세한 건 `references/parsing.md`.

### Phase 4 — 5대 체크리스트

판정 기준 전체는 `references/checklist.md`에 있다. 요약:

| # | 항목 | 무엇을 보나 | 근거 |
|---|---|---|---|
| 1 | **쿼터 일치** | 응답자 특성 표의 셀별 사례수가 목표 할당과 맞는가, 합이 전체 N인가 | 설문지 쿼터표 |
| 2 | **Base 확인** | **모든 문항**. base 정의(문구)와 사례수가 기대와 맞는가 | 설문지 base 지시문 |
| 3 | **로직 Check** | base/prog 로직대로 응답자 수가 줄었는가, 스킵·이탈이 반영됐는가 | 앞 문항 테이블 사례수 |
| 4 | **Code 일치** | 보기 코드와 문구가 설문지와 같은가, 순서·역코딩·넷팅 방향이 맞는가 | 설문지 보기 목록 |
| 5 | **문번 확인** | 넘버링 누락·중복·순서 뒤바뀜, 가이드 대비 표 누락 | 설문지·가이드 순서 |

여기에 **구조 검수**를 더한다 (사용자 요구 사항):
- 한 표에 **문항이 두 개 이상** 섞여 들어가지 않았는가
- 한 문항 안에서 **보기 번호가 중복**되지 않는가
- **빠진 보기**가 없는가 → 있으면 해당 셀 값이 0인지 확인. 0이면 `07_미출력보기`로, 0이 아니면 이슈
- 설문지 보기 문구와 테이블 행 라벨이 **글자 단위로** 같은가 (공백·괄호·단위 표기 차이도 기록)
- 가이드의 행·열 구조가 테이블에 그대로 산출됐는가 (배너 열 수·순서·넷팅 행 위치)

### Phase 5 — 오탐 제거

건너뛰지 않는다. 자주 나오는 오탐:

| 증상 | 진짜 원인 |
|---|---|
| 보기 라벨 불일치 대량 | 병합 셀 때문에 라벨이 빈칸으로 읽힘. 원본 격자를 다시 본다 |
| Base 불일치 대량 | 가중사례수 열을 사례수로 읽음 |
| 문번 누락 대량 | 블록 분할 실패로 두 표가 한 블록에 뭉침 |
| 행 수 불일치 | 평균·표준편차·넷팅 행을 보기로 셈 |
| 보기 누락 | 해당 보기 응답이 0건이라 DP가 미출력 (이슈 아님) |

유형별로 묶고 표본을 원본 격자로 재확인한 뒤, 제외한 건수와 사유를 기록한다.

### Phase 6 — 엑셀 리포트

검수 결과를 `findings.json`으로 쓰고 변환한다.

```bash
python scripts/make_report.py findings.json -o "테이블검수_<프로젝트>_<YYYYMMDD>.xlsx"
```

스키마는 `references/report-schema.md`, 예시는 `assets/findings_example.json`.
시트 구성 (고정):

| 시트 | 내용 |
|---|---|
| `00_검수요약` | 프로젝트 정보, 5대 체크리스트 결과, 이슈 건수(치명/중요/확인필요) |
| `01_문항별검수` | **전 문항 1행씩** — 검수했다는 사실 자체가 산출물 |
| `02_이슈목록` | 심각도·문번·유형·현상·근거·조치요청 |
| `03_쿼터확인` | 셀별 목표/실제/차이/판정 |
| `04_Base로직` | 로직 문장 → 기대 base → 실제 N → 판정 |
| `05_행열구조` | 가이드 대비 행·열 구조 대조 |
| `06_보기코드대조` | 문항×보기 단위 코드·문구 대조 |
| `07_미출력보기` | 0건이라 빠진 보기 (참고, 이슈 아님) |
| `08_검증범위` | 검증한 항목 / 검증하지 못한 항목 |

**모든 문항이 `01_문항별검수`에 나와야 한다.** 이상 없는 문항도 "적합"으로 한 줄 남긴다.
연구원이 DP실에 회신할 때 "무엇을 봤는지"가 근거가 된다.

### Phase 7 — 사용자 보고

터미널에는 요약만 낸다: 총 문항 수, 확정 이슈 수(심각도별), 확인 필요 건수,
그리고 **DP실에 바로 붙여 보낼 수 있는 수정 요청 문장**. 파일 경로를 함께 준다.

## 판정 등급

| 등급 | 의미 | 색 |
|---|---|---|
| `적합` | 설문지·가이드와 일치 확인 | 초록 |
| `이상` | 명백한 오류. DP 수정 필요 | 빨강 |
| `확인필요` | 동작은 확인됐으나 의도인지 판단 불가. 연구원이 답해야 함 | 노랑 |
| `참고` | 이슈 아님. 기록만 (0건 미출력 등) | 회색 |
| `미검증` | 이 방법으로 확인 불가 | 회색 |

애매하면 `이상`이 아니라 `확인필요`로 둔다. 오탐 한 건이 리포트 전체의 신뢰를 깎는다.

## 매 회차 독립

설문지·가이드·테이블 세트는 매번 완전히 새 것으로 취급한다.
이전 회차의 문번 체계, 배너 구조, 보기 코드를 **가정하지 않는다.**
가져오는 것은 이 스킬의 절차와 판정 기준뿐이다.
