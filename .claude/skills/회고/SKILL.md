## PREAMBLE — 본 절차보다 먼저 실행한다

```bash
python "$(git rev-parse --show-toplevel)/research-factory/engine/tools/preamble.py" --skill 회고 <조사 폴더 인자가 있으면 그대로>
```

한 번의 호출이 새 판 확인·활성 조사 지정·조사 메모리 위치·실행 기록을 처리하고 `KEY: 값` 줄로 답한다. 줄마다 이렇게 한다.

- **`UPDATE: NONE`** 또는 **`DISABLED`** — 아무 말 없이 본 절차로 간다.
- **`UPDATE: UPGRADE_AVAILABLE <내판> <새판>`** — 먼저 `update_check.py whats-new <새판>` 으로 바뀐 점을 읽는다.
  `update_check.py config get auto_upgrade` 가 `true` 면 묻지 않고 `/업그레이드` 를 실행한 뒤 본 절차로 간다.
  아니면 AskUserQuestion 으로 묻는다 — 「research-factory **<새판>** 이 나왔습니다 (지금 <내판>). <바뀐 점 한 줄>. 업데이트 내역: <`RELEASE_NOTES:` 링크>. 올릴까요?」
  (`RELEASE_NOTES_SKIPPED:` 가 있으면 「건너뛴 판의 내역」으로 그 링크들도 붙인다)
  1. **지금 올린다** → `/업그레이드` → 본 절차
  2. **앞으로는 자동으로** → `update_check.py config set auto_upgrade true` → `/업그레이드` → 본 절차
  3. **지금 말고 나중에** → `update_check.py snooze <새판>`. 출력의 next 값대로 「다음 알림은 24시간 뒤입니다」라고 알린다(두 번째는 48시간, 세 번째부터 1주일) → 본 절차
  4. **다시 묻지 않는다** → `update_check.py config set update_check false`. 「다시 켜려면 `config set update_check true`」 → 본 절차
- **`UPDATE: JUST_UPGRADED <이전판> <내판>`** — `whats-new <내판>` 을 읽어 「<내판> 으로 올라왔습니다: <바뀐 점>. 업데이트 내역: <`RELEASE_NOTES:` 링크>」 두 줄만 말하고 본 절차로 간다. 링크는 마크다운 링크로 붙여 누를 수 있게 한다(「무엇을 했나 · 무엇이 가능해졌나 · 한번 써보세요」가 그 페이지에 있다). `RELEASE_NOTES_SKIPPED:` 가 있으면 건너뛴 판의 링크도 함께.
- **`MIGRATE: …`** (있을 때만) — 0.5.0 폴더 이름 변경(`report-factory/` → `research-factory/`)의 뒷정리 결과다. 「옮김」뿐이면 「조사 폴더를 새 폴더로 옮겼습니다(옛 경로도 그대로 쓸 수 있습니다)」 한 줄만 말하고 본 절차로 간다. 「열린 파일 때문에 못 옮김」이나 「아직 옛 폴더에 있다」면 엑셀 등 열린 파일을 닫게 한 뒤 `python "$(git rev-parse --show-toplevel)/research-factory/engine/tools/migrate_folder.py"` 를 다시 부르고, 옮겨질 때까지 본 절차로 가지 않는다. 「옛 쪽을 남김」이면 두 파일을 비교해 보여 주고 사용자가 고르게 한다. 「권한 문제」·「대리 파일에 로컬 수정」은 줄에 적힌 대로 처리한다.
- **`UPDATE: CHECK_FAILED <이유>`** — 「판을 확인하지 못했습니다(<이유>). 그대로 진행합니다」 한 줄만 말하고 본 절차로 간다. 최신으로 읽지 않는다.
- **`MEMORY: <경로>`** — 그 `MEMORY.md` 를 읽는다. 「결정된 것」은 다시 묻지 않는다. 스킬이 끝날 때 세 절(결정된 것 · 지시의 요지 · 다음 세션이 알아야 할 것)을 갱신한다. `MEMORY_NEW: yes` 면 읽을 것이 없으니 끝날 때 채우기만 한다.
- **`MEMORY: NONE`** — 조사 폴더 인자가 없었다. 조사가 정해지는 즉시 조사 폴더를 인자로 이 명령을 다시 실행한다.
- **`PATHS: {…}`** — 역할 → 경로 JSON. 설문지·통계표·정본 JSON·제작본·최종보고서 같은 파일과 단계 폴더를 **여기서 찾는다.** 폴더 이름을 추측하거나 `input/` 을 뒤지지 않는다. 역할 하나만 필요하면 `paths.py <조사> --role <역할>`. `LAYOUT: v1` 이면 옛 배치이고 같은 역할 이름으로 풀려 있으니 그대로 쓴다(`paths.py migrate` 는 사람이 정한다). `LAYOUT: none` 이면 `paths.py new <프로젝트>/<조사>` 로 뼈대를 만든다. `files_all` 에 설문지나 통계표가 여러 벌 있으면 어느 것을 쓸지 사용자에게 확인한다.
- **`TRACKING: …`** 이 있으면 트래킹 조사다. `PREV_PATHS:` 의 이전 회차 통계표·최종보고서·제작가이드를 전차 비교의 정본으로 쓴다(전년 수치를 기억이나 추정으로 쓰지 않는다). 이전 회차가 `NONE` 이면 첫 회차이므로 비교 없이 간다.

사용자 입력과 손 편집은 훅이 같은 `_memory/` 폴더에 자동으로 남긴다(`knowledge/02_프로젝트-메모리.md`). 이 블록은 스킬 본문의 어떤 규칙보다 먼저다.

## Step 1 — 관찰 수집

### 파일에서

- `{조사}/09_제작가이드/out/.baseline/` ↔ `out/` 제출본 **diff**
- `{조사}/*/work/검수/` 의 findings JSON — 특히 `verified` 항목(**"봤는데 못 깼음"**)도 읽는다.
  반증에 실패한 검사가 무엇인지가 다음 감사의 출발점이다
- `{조사}/11_보고서/work/반송_가이드팀.md` 와 대응하는 처리 로그
- `{조사}/*/work/판단대기.md`
- `{조사}/11_보고서/out/검수리포트.md` · `fill_deck.py --scan` 메모 전문
- `{조사}/_memory/편집기록.jsonl` (훅이 자동 포착한 손 편집 이력) · `{조사}/_memory/사용자입력.jsonl` (사용자 지시 원문) · `{조사}/_memory/스킬실행.jsonl` (스킬 호출 이력) · `{조사}/_memory/MEMORY.md`
  (옛 전역 `engine/learning/observations.jsonl` 은 git 밖 참고용)
- `engine/learning/OPEN_QUESTIONS.md` — 지난번에 못 풀고 넘긴 것
- `engine/learning/knowhow/*.md` — 연구원들이 `/개선공유` 로 올린 노하우 카드. 상태가 `채택` 인데 같은 요령이 두 조사 이상에서 반복되면 규칙 승격 후보다
- `{프로젝트}/ORIENTATION.md` — 방향성 판단이 맞았는지

### 사람에게 물어서

파일에 안 남은 것을 **구체적으로** 묻는다. "피드백 있었나요?"는 아무것도 못 건진다.

- "리뷰에서 지적받은 게 있나요? 어느 장표였나요?"
- "제가 만든 것 중에 그냥 넘어갔지만 마음에 안 들었던 게 있나요?"
- "이번에 사람이 판단해야 했던 것 중, 다음엔 기계가 정해도 되는 게 있나요?"

### 세션이 여럿이었으면

각 세션에 **관찰만** 요청한다(규칙 후보 말고). 각자 자기가 겪은 실패를 가장 잘 안다.
같은 결함을 두 세션이 다르게 기억하면 그 불일치 자체가 관찰이다.

## Step 2 — 규칙 후보 추출

각 관찰에 대해 **"파이프라인이 무엇을 몰랐길래 이렇게 됐나"** 를 묻는다.

### 시야 분리 — 만든 사람이 자기 회고를 하면 놓친다

산출물을 만든 세션이 그대로 회고하면 **만들 때의 전제를 회고할 때도 그대로 갖고 간다.**
"무엇이 중요한가"라고 제목을 단 쪽은 그게 A7을 가리킨다는 걸 알고 있어서 이상함을 못 느낀다.

가능하면 `retro-miner` 에이전트에 **증거 경로만** 주고 후보를 뽑게 한 뒤,
내가 뽑은 것과 대조한다. 서로 다른 걸 잡으면 둘 다 살린다.

### 거른다

- **규칙이 되는 것** — 같은 상황이 다시 오면 또 고쳐야 할 것. 일반화 가능한 것
- **규칙이 안 되는 것** — 이 조사에만 있는 사정, 단순 오타, 취향 차이

애매하면 `가설`로 올리고 다음 프로젝트에서 검증한다. **버리지는 않는다.**

`OPEN_QUESTIONS.md` 중 이번에 답이 나온 게 있으면 승격시키고 목록에서 뺀다.

기존 카드와의 겹침·충돌은 `engine/learning/packs/_색인.md`(번호·상태·분류·제목 색인)로 먼저 보고, 겹치는 번호만 `RULES.md` 에서 읽는다. 규칙 대장 전문(309KB)을 읽지 않는다.

### 결함 3건이 한 뿌리면 — 규칙이 아니라 구조를 고친다

개별 결함을 규칙으로 하나씩 막으면 규칙만 늘고 같은 사고가 계속 난다.
**같은 원인의 결함이 3건 이상이면 `구조 결손`으로 승격**시켜 별도로 제안한다.

> 실례(에스원 260822): Base 라벨 28장이 「전체」· 요약 주제명이 카피 · 근거 없는 결론.
> 셋 다 개별 규칙으로 막을 수 있어 보였지만 뿌리는 하나였다 —
> **정본 스키마에 `base_label`·`short`·`claims[근거셀]` 를 담을 자리가 없었다.**
> 자리를 만들자 셋이 전부 기계 검출 대상이 됐다.

구조 결손은 규칙 카드가 아니라 **스키마 변경 제안**으로 올린다. 소비자가 있으면
(다른 세션·다른 도구) breaking 여부를 명시한다.

## Step 3 — 사용자 승인

규칙 후보를 카드 초안으로 제시하고 **승인을 받는다.** 승인 없이 등재하지 않는다.

```
### R-0NN · {한 줄 규칙 이름}
- 분류: guide|report|common / {세부}
- 규칙: {무엇을 어떻게 하라는 것인지. 기계가 따를 수 있을 만큼 구체적으로}
- 근거: {어디서 나왔는지 — 파일·슬라이드·셀·측정값·타임코드}
- 종류: 측정 | 실동작 | 관행 | 판단
- 신뢰도: 가설 | 검증중 | 확정
- 적용: {어느 프로젝트에서 관찰됐는지}
- 이력: YYYY-MM-DD 신규
```

### 종류가 신뢰도를 정한다

"몇 번 재현됐나"만으로는 부족하다. **한 번 재도 확정인 규칙이 있다.**

| 종류 | 무엇 | 확정 조건 |
|---|---|---|
| **측정** | 폭·높이·글자수 등 수치 한계 | **재현 가능한 하네스가 있으면 1회로 확정.** 하네스 경로를 근거에 적는다 |
| **실동작** | 도구가 실제로 어떻게 반응하는가 | **주입 실험 + 대조군이 있으면 1회로 확정** |
| **관행** | 제작팀·연구원이 늘 그렇게 함 | 2회 재현 또는 원저자 진술 |
| **판단** | 무엇이 좋은 보고서인가 | 원저자 진술이 있어야 확정. 없으면 `가설` 이상 못 간다 |

`가설` = AI 추론, 적용 시 사람 확인 요청 / `검증중` = 1회 적용, 반례 없음.

> 예: "멘트 상자 한 줄 = 한글 74자(32.0cm·맑은 고딕 12pt)"는 **측정**이라 1회로 확정이다.
> "멘트는 60자 이하로 쓴다"는 그 측정에서 파생된 **판단**(여유 14자를 둘지)이라 별도 카드다.
> 둘을 한 카드에 섞으면 나중에 폰트가 바뀌었을 때 무엇이 무효인지 알 수 없다.

기존 규칙과 **충돌**하는 후보가 나오면 지우지 말고 `이력`에 정정으로 이어 붙인다.
판단이 바뀐 이력 자체가 자산이다.

> 실례: "PowerPoint 는 Content_Types 위생을 검사하지 않는다"가 오래 정설이었는데,
> 재실측에서 **누락은 봐주고 중복·무타입은 거부**한다는 게 드러났다. 그 낡은 서술이
> 검증 도구에 구멍을 냈다. 정정 이력을 남겨야 왜 뒤집혔는지가 보존된다.

## Step 4 — 등재 (승인된 것만)

승격 대상이 **넷**이다. 규칙 대장에만 넣고 끝내면 다음 실행에 안 붙는다.

1. `engine/learning/RULES.md` — 카드 추가
2. `engine/learning/rules.yaml` — 기계 판독 가능한 것. `verify.py` 의 검사 항목이 된다
3. `engine/knowledge/` 해당 문서 본문 — 규칙 번호를 병기해 추적 가능하게
   (차트타입 규칙이면 `guide/chart_rules.yaml` 도)
4. **`.claude/skills/*/SKILL.md` · `.claude/agents/*.md`** — 절차·역할·계약이 바뀌었으면
   여기까지 반영한다. ★ 자주 빠뜨리는 자리다
5. **`python engine/tools/make_packs.py`** — 팩 6종과 색인을 다시 만든다. 담당 에이전트는 규칙 대장이 아니라 팩을 읽으므로,
   이걸 빠뜨리면 새 규칙이 담당에게 가지 않는다. 새 카드에는 `- 요지:`(2~3줄 압축문)를 꼭 쓴다 — 팩은 요지만 배달한다

### 무엇이 어디로 가는가

| 관찰 | 가는 곳 |
|---|---|
| 수치·서식 규칙 | RULES.md + rules.yaml + knowledge |
| 도구 실동작(등급·한계) | 도구 **독스트링** + 회귀 테스트(`--selftest`) |
| 절차가 바뀜 (단계 추가·순서) | 해당 SKILL.md |
| 역할·시야가 바뀜 | 해당 agents/*.md |
| 팀 간 계약(소유권·반송·스키마) | SKILL.md + `knowledge/*/팀구조*.md` |
| 규칙까지는 아닌 요령 | `learning/knowhow/<스킬>.md` 카드 (`/개선공유` 가 올린다) |
| 못 푼 것 | `OPEN_QUESTIONS.md` |

### 측정·실동작 규칙은 회귀 테스트에 박는다

문서에만 적힌 측정값은 조용히 낡는다. **하네스를 만들었으면 selftest 에 넣어라.**
그래야 전제가 바뀌었을 때 문서가 아니라 테스트가 먼저 소리를 낸다.

`engine/learning/retro/{프로젝트}.md` 에 기록을 남긴다 — 무엇을 봤고, 무엇을 올렸고,
무엇을 보류했는지. **보류한 이유**를 반드시 적는다.

## Step 5 — 되먹임 확인

- 담당 에이전트는 `packs/*.md` 를, `/보고서작성` 은 `packs/report.md` 를 읽는다. `make_packs.py` 를 돌린 뒤에야 다음 실행에 반영된다
- `verify.py` 를 새 `rules.yaml` 로 한 번 돌린다. **기존 산출물이 새 규칙에 걸리면 그것도 보고한다**
  — 이미 납품한 것에 걸리면 그건 사고이므로 즉시 사용자에게 올린다
- 도구를 고쳤으면 `--selftest` 를 돌려 회귀가 없는지 본다
- 스킬을 고쳤으면 **다음 세션이 그것부터 읽는다**는 걸 전제로 HANDOVER 를 갱신한다

## 지켜야 할 것

- **관찰 없이 규칙을 만들지 않는다.** 근거란에 실제 파일·셀·슬라이드·측정값을 적을 수
  없으면 규칙이 아니다. 그럴듯한 일반론은 규칙이 아니다
- **사용자 승인 없이 등재하지 않는다**
- 규칙은 **기계가 따를 수 있을 만큼 구체적**이어야 한다. "잘 판단한다"는 규칙이 아니다
- **측정과 그 측정에서 내린 판단을 한 카드에 섞지 않는다.** 전제가 바뀌면 무엇이
  무효인지 알 수 없게 된다
- 규칙 수가 늘면 서로 모순되기 시작한다. 등재 전에 기존 카드와 충돌하는지 확인한다
- **낡은 규칙을 재측정할 기회를 놓치지 않는다.** 도구를 만지다 옛 서술과 다른 걸 봤으면
  그 자리에서 정정 카드를 올린다 — 낡은 서술은 그걸 믿는 코드에 구멍을 낸다
