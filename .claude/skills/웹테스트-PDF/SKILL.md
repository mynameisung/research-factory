# 설문 웹테스트 자동화

연구원이 손으로 하던 설문 웹테스트를 자동화한다. 원안(Word)대로 웹이 구현됐는지를
**실제로 클릭하며 주행**해 검증하고, 이상 항목을 보고서로 낸다.

## 핵심 원칙

**1. LLM을 루프 안에 넣지 마라.**
판단은 앞뒤에서만 한다 — 앞에서 Word를 읽어 명세를 만들고, 뒤에서 이상 항목을 리뷰한다.
중간의 수천 번 클릭은 전부 코드가 한다. 스크린샷을 매 클릭마다 찍으면 페이지당 5~15초가
걸려 100문항 설문 하나에 몇 시간이 든다. DOM으로 돌리면 **페이지당 약 180ms**다.

**2. 오탐 제거는 선택이 아니라 필수다.**
탐지기는 반드시 오탐을 낸다. 실측 사례로 1,107건 경보 중 확정 이슈는 10건이었다.
재현 검증(Phase 7)을 건너뛰고 원시 경보를 보고하면 연구원의 신뢰를 잃는다.

**3. 봇이 통과한 것과 사람이 쓸 수 있는 것은 다르다.**
`element.checked = true`로 강제 선택하면 실제로는 클릭 불가능한 요소도 통과한다.
strict 모드(순수 클릭만)를 반드시 함께 돌린다.

**4. 쿼터가 걸린 설문은 시나리오마다 쿼터 셀을 흩어라.**
성별·연령·지역 등에 쿼터가 있는 설문에서 같은 셀로 반복 투입하면 그 셀이 마감되어
**정상 로직도 "현재 조사에 참여하실 수 없습니다"로 보인다.** 실측 사례로 87개 중 40개(46%)가
이 화면으로 끝나 중대 결함처럼 보였으나, 쿼터 셀을 분산하니 전부 정상이었다.
원안에서 `[QUOTA]` 표기를 먼저 찾고, 시나리오마다 성별·지역·연령·기타 쿼터 변수를 순환시킨다.
쿼터와 무관한 검증(보기 제시조건·로테이션·BASE)일수록 셀 분산이 중요하다.

**5. 실사중 설문에는 절대 실행하지 않는다.**
진행 상태가 "테스트중"인지 먼저 확인한다. 테스트 응답은 실사 전 정리가 필요하다는 점을
보고서에 명시한다.

## 진행 순서

### Phase 0 — 입력 확인

사용자에게서 받는다:
- **설문 원안** — `.docx` 또는 붙여넣은 텍스트/스크립트 소스
- **테스트 URL** — 예: `https://survey.panel.co.kr/SurveyTest.asp?alias=<alias>`
- (선택) **페이지별 TEST URL** — 문구/테이블 구조 확인용

확인할 것:
- 진행 상태가 **테스트중**인가 (실사중이면 중단하고 사용자에게 알린다)
- URL이 로그인 없이 열리는가 (대개 alias만으로 열린다)

### Phase 1 — 원안을 명세로

**정규식 파서를 만들지 마라.** 원안 포맷은 회사·연구원마다 다르다.
직접 읽고 `spec.json`을 작성한다. `.docx`는 다음으로 텍스트를 뽑는다:

```bash
python scripts/read_docx.py <원안.docx> > spec_raw.txt
```

문단뿐 아니라 **표, 런 단위 색상·취소선**까지 나온다. 이탈·로테이션 표기가
색이나 취소선으로 되어 있는 경우가 많으므로 반드시 확인한다.

스키마는 `references/spec-schema.md`를 따른다. 핵심 필드:
문항코드, 문항문구, 응답유형, 보기목록, 필수여부, 로테이션 대상, 고정 보기,
파이핑 참조, 분기 로직(스킵/이탈/배타), 최소·최대 선택 수.

원안에 로직이 안 적혀 있어도 괜찮다. Phase 2에서 실측하고, Phase 3에서
"원안에 명시 없음 — 실측 결과 이러함"으로 보고하면 된다.

### Phase 2 — 전이표 실측

**이 단계가 이 스킬의 핵심이다.** 웹의 실제 분기 구조를 코드로 알아낸다.

먼저 엔진 어댑터를 확정한다. 엠브레인 계열이면 `references/engine-embrain.md`가
이미 완성된 어댑터를 담고 있으니 그대로 쓴다. 다른 엔진이면 같은 문서의
"새 엔진 어댑터 만들기" 절차를 따른다.

그다음 **각 문항의 각 보기를 눌러 어디로 가는지** 기록한다:

- 세션 하나가 문항 i에서 보기 (k mod n_i)를 고르는 방식으로 max(보기수)개 세션을 돌린다
- 관측 못 한 (문항, 보기) 쌍은 명시적 계획으로 채운다
- **보기 텍스트가 아니라 `value` 속성으로 기록한다.** 라벨 추출은 스킨에 따라
  옆 보기 텍스트까지 뭉쳐 잡히는 일이 흔하고, 그러면 "어느 보기가 어디로 가는지"가
  통째로 틀린다

산출: `transitions.json` — `{문항: {보기값: 다음문항}}`

여기서 **결정점**(보기에 따라 다음 문항이 달라지는 문항)이 자동으로 드러난다.

### Phase 3 — 원안 대조 + 로직 구현 현황표

`spec.json` × `transitions.json`을 맞춰본다. 잡히는 것:

- 원안에 있는데 웹에 없는 문항 / 웹에만 있는 문항
- 보기 개수·문구 불일치, 순서 불일치
- 원안의 스킵·이탈 로직과 실측 전이표의 불일치 ← **가장 중요**
- 원안에 없는 분기가 웹에 있음 (반대도)

#### 로직 구현 현황표 — 이 스킬의 핵심 산출물

**원안에 로직이 안 적혀 있는 경우가 대부분이다.** 연구원이 Word에 문항과 보기만 쓰고
로직은 스크립터에게 구두로 전달했거나, 원안 자체가 문항 목록일 뿐인 경우가 많다.
그러면 "원안대로인가"를 물을 수가 없다.

이럴 때 훨씬 유용한 것은 방향을 뒤집는 것이다. 실측 전이표를 **사람이 읽을 수 있는
로직 문장으로 되돌려주고, 이게 의도한 것이 맞는지 확인받는다.**

> "D1에서 '시스템 없음'을 고르면 D2~D6이 건너뛰어지고 E1로 갑니다. 맞습니까?"

전이표의 모든 결정점을 한 줄씩 문장으로 옮기고, 각각을 세 가지로 분류한다:

| 분류 | 기준 |
|---|---|
| **정상 확인** | 실측으로 동작이 확인됐고, 상식적으로나 원안 근거로 의도가 명확한 것 |
| **확인 필요** | 동작은 확인됐으나 의도인지 판단할 수 없는 것. 연구원이 답해야 한다 |
| **이상** | 명백히 잘못된 것. 확정 이슈 목록으로 넘어간다 |

**확인 필요로 분류해야 하는 전형적인 신호**:

- 응답자 유형에 따라 **받는 문항 수가 크게 다른 경우** (예: A형 50문항 vs B형 38문항).
  의도된 설계일 수도 있지만, 조건문이 잘못 걸려 한쪽이 통째로 누락된 것일 수도 있다
- 척도 문항의 **중립 보기("보통이다")가 어느 쪽으로 분류되는지**.
  긍정 쪽으로 묶여 후속 문항이 스킵되면 표본이 예상보다 줄어든다
- 조건부 비활성화·표시 조건이 **일부 보기에만 걸려 있고 인접 보기에는 없는 경우**
- 배타 보기를 골랐을 때의 **점프 목적지가 유형별로 다른 경우**
- 원안에 근거를 찾을 수 없는 분기

이 표는 확정 이슈 목록과 **별도로** 보고서에 넣는다. 이슈가 아니기 때문이다.
연구원이 표를 훑으며 "이건 맞고 저건 틀렸다"고 답하면, 그 답이 다음 회차의
`spec.json` 로직 절이 된다. 회차를 거듭할수록 원안 대조가 정확해진다.

**덧붙여 반드시 명시할 것**: 이 방법으로 **검증할 수 없는 로직**도 함께 나열한다.
쿼터·할당, 이어하기, 중복 응답 차단, 저장 변수 매핑, 시간 기반 게이트가 여기 속한다.
"확인했다"와 "확인하지 못했다"를 섞으면 안 된다.

### Phase 4 — 시나리오 설계 (MECE)

시나리오 수는 감으로 정하지 않는다. **계산한다.**
산정법 전체는 `references/coverage-design.md`에 있다. 요약하면:

| 커버리지 | 필요 수 | 무엇을 잡나 |
|---|---|---|
| 경로 커버리지 | 결정점 분기 수의 곱 | 스킵·이탈·분기 로직 전부 |
| 보기 커버리지 | max(보기 수) | 보기 누락, 선택 불가 보기 |
| 로테이션 표본 | `ln(n²/0.05) / ln(n/(n-1))` | 로테이션 미작동, 고정 보기 오류 |
| 음성 테스트 | 문항 수 | 필수응답 검증 누락 |

경로 커버리지가 실질적 상한이다. **전조합은 계산하지 마라** — 척도 문항이
13개만 있어도 5¹³이라 10¹⁸ 단위가 되고, 이건 무한이 아니라 "유한하지만 도달 불가능"이다.
사용자가 "전부"를 요구하면 이 숫자를 보여주고 경로 커버리지로 합의한다.

각 시나리오는 **결정 벡터**로 표현한다: `{SQ1:1, D1:3, E1:'none', E2:2, F1:5, ...}`.
결정점이 아닌 문항은 아무 보기나 골라도 경로가 같으므로, 보기 커버리지를 채우는 데
활용한다 (같은 경로를 도는 시나리오끼리 서로 다른 보기를 고르게 배분).

### Phase 5 — 병렬 실행

두 가지 모드가 있다.

**quick 모드** — 설치 없이 즉시. Claude의 브라우저 창에서 iframe 여러 개를 띄워 돌린다.
같은 출처이므로 부모 JS 컨텍스트가 살아 있어 툴 호출 한 번으로 전체 주행이 끝난다.
`assets/runner.js`를 `javascript_tool`로 주입한다. 화면에 격자로 보여 사용자가 지켜볼 수 있다.
10~50 시나리오에 적합.

**full 모드** — Playwright. 브라우저 컨텍스트가 완전히 분리되어 세션 충돌 위험이 없고,
스크린샷·비디오·trace를 남길 수 있으며 수백~수천 시나리오를 감당한다.

```bash
python scripts/run_playwright.py --url <TEST_URL> --scenarios scenarios.json --workers 10 --out results.json
```

주의: `javascript_tool`은 30초에 끊긴다. quick 모드는 **즉시 반환 후 폴링** 방식으로 짠다
(`window.__WT`에 결과를 넣고 별도 호출로 회수). `assets/runner.js`가 이미 그렇게 되어 있다.

### Phase 6 — 검수 레이어

주행하면서 전부 함께 본다:

1. **로직** — 실제 경로가 시나리오의 결정 벡터대로 갔는가
2. **이탈** — 이탈 조건에서 종료 화면에 도달하는가, 종료 문구가 맞는가
3. **파이핑** — 앞 문항에서 고른 값이 뒤 문항 문구에 정확히 들어가는가.
   순위형은 1순위·2순위가 뒤바뀌지 않는가. "기타" 직접입력 값도 그대로 나오는가
4. **로테이션** — 노출마다 보기 순서가 바뀌는가, 각 보기가 각 위치에 고르게 나오는가,
   **"기타"·"없음"·"해당사항 없음"이 항상 끝에 고정되는가**
5. **필수응답** — 무응답으로 다음을 눌렀을 때 차단되는가 (`window.alert`를 가로채면
   경고창에 막히지 않고 전 문항을 훑을 수 있다)
6. **문구** — 원안 대비 누락·오탈자, 경고 문구의 문항번호가 맞는가,
   문자 깨짐·HTML 태그 노출
7. **진행률** — 역행하지 않는가, 마지막 문항 전에 100%에 닿지 않는가

디테일과 판정 기준은 `references/checks.md`에 있다.

### Phase 7 — 오탐 제거 (건너뛰지 말 것)

원시 경보를 그대로 보고하면 안 된다. 반드시:

1. 경보를 유형·문항별로 묶는다
2. **각 유형마다 독립 세션으로 재현을 시도한다**
3. 재현되지 않거나, 원인이 러너 쪽으로 밝혀진 것은 제외한다
4. 제외한 내역을 건수와 사유와 함께 보고서에 남긴다 (투명성)

실측에서 자주 나오는 오탐:

| 증상 | 진짜 원인 |
|---|---|
| "응답 위젯 없음" 대량 | 안내문 페이지. 본문의 "응답해 주세요"를 문항으로 오인 |
| "보기 텍스트 없음" 대량 | 스킨에 `<label>`이 없어 추출 실패. 화면엔 정상 표시 |
| "빈 페이지" | 로드 직후 읽은 경쟁 조건. 안정화 대기 후 재확인하면 사라짐 |
| "진행 불가" 대량 | 순위형에서 같은 보기를 두 번 눌러 선택이 해제됨 (러너 버그) |
| 경고문 문항번호 불일치 | 라벨 추출이 옆 보기까지 뭉쳐 잡음. `value`로 재확인 |

반대로 **진짜인데 놓치기 쉬운 것**: 완주했는데 종료 문구가 "대상이 아닙니다"인 경우.
조기 이탈이 아니라 끝까지 답한 뒤 이탈 처리되는 것이라 경로 길이를 함께 봐야 잡힌다.

### Phase 8 — 보고서

`assets/report_template.html`을 채워 HTML을 쓰고 PDF로 변환한다.

```bash
powershell -File scripts/make_pdf.ps1 -Html <리포트.html> -Pdf <출력.pdf>
```

Chrome 헤드리스를 쓰되 **전용 `--user-data-dir`을 반드시 지정한다.** 없으면 기존
Chrome 프로세스와 충돌해 조용히 실패한다. 출력 경로에 한글이 있으면 실패하므로
ASCII 임시 경로로 만든 뒤 복사한다. 스크립트가 둘 다 처리한다.

보고서 구성:
1. 요약 (시나리오 수, 페이지 수, 소요 시간, 확정 이슈 수)
2. 확정 이슈 — 등급·문항·재현 횟수·증상. 등급은 응답자 노출도 기준
3. 정상 확인 항목 — 검증했고 문제없던 것 (이게 있어야 커버리지가 보인다)
4. 파이핑·로테이션 상세
5. 오탐 제외 내역
6. 커버리지 (경로 수, 도달 문항, 미도달 구간)

이슈 등급:
- **HIGH** — 응답자가 직접 겪는 것 (오작동 문구, 진행률 역행, 잘못된 이탈, 진행 불가)
- **MED** — 응답에 영향 가능 (안내 문구 누락, 오탈자, 일관성 결함)
- **LOW** — 사용성·접근성, 확인 권장 사항

## 한계 — 보고서에 반드시 명시할 것

이 방법으로 **잡을 수 없는 것**이 있다. 검증했다고 말하면 안 되는 영역이다.

- **저장 데이터** — 화면이 맞아도 DB에 다른 변수로 들어갈 수 있다. 로테이션된 보기를
  눌렀을 때 화면 순서가 아닌 원래 코드값이 저장돼야 하는데, 이게 틀리면 집계가 전부
  어긋난다. **웹 테스트로는 절대 못 잡는다.** 테스트 응답 후 실제 저장 테이블을
  조회해 대조해야 완전하다
- **시각적 결함** — DOM에 텍스트가 있어도 화면에서 안 보일 수 있다(가려짐, 잘림,
  색 겹침, 표 깨짐). 스크린샷 검토가 병행돼야 한다
- **모바일 실기기** — 터치 이벤트, 소프트 키보드, iOS Safari 특유 동작
- **시간 기반 로직** — 안내문 N초 후 버튼 활성화 같은 것. 봇은 즉시 누르므로
  게이트가 있어도 눈치채지 못한다. 별도로 버튼 상태를 100ms 간격으로 관찰해야 한다
- **서버 상태** — 쿼터 마감, 동시 접속 폭주, 이어하기, 중복 응답 차단
- **의미적 오류** — 오탈자나 논리적으로 말이 안 되는 문항 순서는 규칙으로 못 잡는다.
  원안 대조와 사람·LLM 검토가 필요하다
