# 검수 항목별 판정 기준

Phase 6에서 주행 중 수집하고, Phase 7에서 재현으로 걸러내는 7개 레이어의 판정 기준이다.
각 레이어마다 **무엇을 보는가 / 어떻게 측정하는가 / 무엇이 이상인가 / 흔한 오탐과 구분법**을 정의한다.

이 문서의 판정 기준은 대부분 **실측에서 나온 진짜 이슈와 오탐**을 근거로 만들어졌다.
근거가 된 실측 사례는 각 절에 인용해 두었고, 전체 목록은 맨 아래 "근거가 된 실측 사례"에 있다.

---

## 0. 모든 레이어에 공통으로 적용되는 규칙

### 0.1 경보와 이슈는 다르다

주행 중 코드가 만드는 것은 **경보(alert)**다. 경보는 보고서에 들어가지 않는다.
Phase 7의 **독립 세션 재현**을 통과한 것만 **확정 이슈(issue)**가 되어 보고서에 들어간다.

> 실측: 1,107건 경보 중 확정 이슈는 **10건**이었다. 나머지 1,097건은 러너 버그이거나
> 탐지기의 오인이었다. 원시 경보를 그대로 냈다면 보고서의 99%가 거짓이었을 것이다.

경보 레코드는 최소한 다음을 담는다. 재현·집계·등급 판정이 전부 이 필드에 의존한다.

```json
{
  "layer": "piping",
  "code": "PIPE_PLACEHOLDER_LEFT",
  "scenario_id": 17,
  "page_no": 23,
  "question": "E2-1",
  "evidence": { "found": "[앞서 선택한 브랜드]", "expected_from": "v12=3" },
  "dom_snapshot": "…판정에 쓴 요소의 outerHTML…",
  "severity_hint": "HIGH",
  "repro_count": 0
}
```

`evidence`에는 **판정에 실제로 쓴 값**을 넣는다. "이상함"이라는 문장만 남기면 재현 단계에서
무엇을 다시 봐야 하는지 알 수 없어 그 경보는 통째로 버려진다.

### 0.2 측정 전 안정화 (경쟁 조건 차단)

페이지 전환은 전체 POST 네비게이션이다. **load 직후에 DOM을 읽으면 빈 페이지로 보인다.**

> 실측 오탐: "빈 페이지" 경보는 전부 로드 직후에 읽은 경쟁 조건이었다. 200ms 대기 후
> 재확인하면 사라졌다.

모든 레이어의 측정은 다음 게이트를 통과한 뒤에만 수행한다.

```js
async function stabilize(doc, wait = 200, tries = 3) {
  for (let i = 0; i < tries; i++) {
    const len = (doc.body && doc.body.innerText || '').trim().length;
    const hasBtn = !!doc.getElementById('smtBtn');
    if (len >= 10 || hasBtn) return true;
    await new Promise(r => setTimeout(r, wait));
  }
  return false; // 여기까지 오면 "진짜 빈 페이지" 후보
}
```

`stabilize()`가 false를 반환한 경우에만 빈 페이지 경보를 낸다. 그 경보도 Phase 7에서
다시 한 번 독립 세션으로 확인한다.

### 0.3 페이지 유형 분류 (안내문 / 문항 / 종료)

**이 분류기가 없으면 오탐의 5분의 1이 여기서 나온다.**

> 실측 오탐: "응답 위젯 없음" 234건이 전부 안내문 페이지였다. 안내문 본문의
> "…응답해 주세요" 같은 문장을 문항 지시문으로 오인한 것이다.

분류는 본문 문구가 아니라 **구조**로 한다.

```js
function classifyPage(doc, codeSet) {
  const widgets = doc.querySelectorAll(
    'input:not([type=hidden]):not([type=button]):not([type=submit]), select, textarea'
  );
  const hasNext = !!doc.getElementById('smtBtn');
  const text = doc.body.innerText || '';
  const codes = [...codeSet].filter(c => new RegExp('(^|[^A-Za-z0-9])' + c + '([^0-9-]|$)').test(text));

  if (!hasNext && widgets.length === 0) return { type: 'END', codes };
  if (hasNext && widgets.length === 0 && codes.length === 0) return { type: 'INTRO', codes };
  if (hasNext && widgets.length === 0 && codes.length > 0) return { type: 'BROKEN_Q', codes };
  return { type: 'QUESTION', codes, widgets: widgets.length };
}
```

- `INTRO` — 다음 버튼은 있는데 입력 요소가 0개이고 **문항코드가 없다**. 안내문. 경보 금지.
- `BROKEN_Q` — 문항코드가 있는데 입력 요소가 0개. **진짜 이슈 후보.**
- `END` — 다음 버튼이 없다. 레이어 2에서 다룬다.

`codeSet`은 정규식으로 추측하지 말고 **`spec.json`의 문항코드 목록을 사전으로 넘긴다.**
코드 체계는 회사·연구원마다 달라서(`SQ1`, `A1`, `E2-1`, `DQ3`…) 패턴 추측은 반드시 틀린다.

> 이 분류가 진짜 이슈를 잡은 사례: **"1개 선택" 안내가 있는데 보기가 하나도 없고
> 주관식 입력창만 있던 문항.** 문항코드가 있으므로 안내문이 아니고, 라디오/체크박스가
> 0개이므로 `BROKEN_Q`로 잡힌다. 234건의 안내문과 이 1건을 가르는 것이 문항코드 사전이다.

### 0.4 보기 텍스트는 못 믿는다 — `value`로 기록한다

> 실측 오탐: "보기 텍스트 없음" **834건.** 척도형 스킨에 `<label>` 태그가 하나도 없어
> 텍스트 추출이 실패한 것이었다. 화면에는 보기가 정상 표시되고 있었다.

엠브레인 척도형 문항의 실제 구조는 이렇다. 보기 텍스트는 라디오와 다른 셀/행에 있다.

```html
<td><p><font><span class="input_rdo">
  <input type="radio" name="v4" id="v4_1_00"><i></i>
</span></font></p></td>
```

id 규칙은 `{name}_{value}_{행인덱스}`이고 행렬형은 `_00, _01, _02…`로 늘어난다.
리스트형(단일선택 목록)은 라벨 추출이 정상 동작하지만 **척도형은 실패한다.**

따라서 두 가지를 분리한다.

| 개념 | 판정 근거 |
|---|---|
| 보기가 **실제로 없다** | `name`이 같은 input의 개수 == 0 |
| 보기 **텍스트를 못 뽑았다** | input 개수 ≥ 1 인데 텍스트가 빈 문자열 |

후자는 **경보가 아니라 측정 실패 표식(`text_unavailable`)**으로 남긴다. 이 한 줄이 834건을 없앤다.

```js
function optionsOf(doc, name) {
  const els = [...doc.querySelectorAll(`input[name="${name}"]`)];
  return els.map(el => ({
    value: el.value,
    id: el.id,
    row: (el.id.split('_')[2] || '00'),
    text: labelTextOf(doc, el) || null,      // 실패하면 null
    kind: rankKind(el)                        // 0.5 참조
  }));
}
```

전이표, 로테이션 분포, 파이핑 대조 — **모든 기록은 `value` 기준으로 한다.**
라벨 추출은 옆 보기 텍스트까지 뭉쳐 잡히는 일이 흔해서, 텍스트로 기록하면
"어느 보기가 어디로 갔는지"가 통째로 틀린다.

### 0.5 순위/복수선택 위젯 조작 규약

```html
<input class="RankTxt" id="RankTxt3" onclick="jFunRank('','3')">
```

`onclick`의 첫 인자가 보기 종류다. **라벨 텍스트를 읽지 않고도 기타/배타 보기를 식별할 수 있다.**

| type | 의미 |
|---|---|
| `''` | 일반 보기 |
| `'t1'` | 기타 (텍스트 입력 연동) |
| `'y'` | 배타 보기 (없음 / 해당사항 없음) |

```js
function rankKind(el) {
  const m = (el.getAttribute('onclick') || '').match(/jFunRank\(\s*'?([^',)]*)'?\s*,/);
  const t = m ? m[1].trim() : '';
  return t === 't1' ? 'other' : t === 'y' ? 'exclusive' : 'normal';
}
```

조작 시 반드시 지킬 두 가지가 있다. 지키지 않으면 **러너가 만들어낸 가짜 이슈**가 대량으로 나온다.

1. **서로 다른 인덱스를 보장한다.** 클릭은 토글이라 같은 보기를 두 번 누르면 해제된다.
   > 실측 오탐: "진행 불가(막힘)" **33건**이 전부 이것이었다. 랜덤으로 두 번 뽑은 인덱스가
   > 겹쳐 선택이 0개가 됐고, 러너는 "필수 문항인데 진행이 안 된다"고 보고했다.

2. **기타는 클릭 → 텍스트 요소 재조회 → 입력 순서로 한다.** 클릭한 뒤에야 텍스트 입력란이
   활성화되므로, 클릭 전에 채운 값은 무효다.
   > 실측 오탐: "기타 선택 시 진행 불가" 경보가 이 순서를 어긴 러너 버그였다.

```js
function pickDistinct(n, k) {
  const idx = [...Array(n).keys()];
  for (let i = idx.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [idx[i], idx[j]] = [idx[j], idx[i]];
  }
  return idx.slice(0, k);
}
```

### 0.6 세션 상태는 히든필드에서 읽는다

쿠키가 아니라 `form2`의 히든필드가 상태 전부를 들고 있다. 측정에 그대로 쓴다.

| 필드 | 쓰임 |
|---|---|
| `id` | 응답자 테스트ID(`CT`로 시작). 경보를 세션에 묶는 키 |
| `ProgressPage` | 현재 페이지번호. 페이지 지문·진행률 교차검증 |
| `last_page` | 총 페이지수 |
| `nextPageAction` | 기본 다음 페이지 파일명(예 `m7.asp`). 분기 판정 보조 |
| `gType` | 분기그룹(A/B) |
| `v1..vN` | 지금까지의 **모든 응답 누적**. 파이핑·분기 검증의 정답지 |

모든 페이지가 `https://survey.panel.co.kr/rSurveyTest.asp`로 POST 자기순환하므로 **URL은 안 바뀐다.**
페이지 동일성 판정에 URL을 쓰면 안 된다. 대신 **페이지 지문**을 쓴다.

```js
const fingerprint = [
  form2.ProgressPage.value,
  [...doc.querySelectorAll('input:not([type=hidden]),select,textarea')].map(e => e.name).sort().join(','),
  codes.join(',')
].join('|');
```

## 1. 로직 — 경로가 결정 벡터대로 갔는가

### 무엇을 보는가

시나리오는 결정 벡터(`{SQ1:1, D1:3, E1:'none', E2:2, …}`)로 표현된다.
그 벡터대로 골랐을 때 **실제로 지나간 문항의 순서**가 Phase 2에서 실측한 `transitions.json`,
그리고 Phase 1의 `spec.json`과 일치하는지를 본다.

세 가지가 서로 다른 대상이다. 헷갈리면 안 된다.

| 대조 | 의미 |
|---|---|
| 실주행 경로 vs `transitions.json` | 웹이 **자기 자신과** 일관적인가 (재현성) |
| `transitions.json` vs `spec.json` | 웹이 **원안대로** 구현됐는가 (Phase 3) |
| 실주행 경로 vs 결정 벡터 | 시나리오가 **의도한 경로를 실제로 탔는가** (커버리지) |

### 어떻게 측정하는가

각 페이지에서 지문과 응답을 기록해 경로 배열을 만든다.

```js
function recordStep(doc, chosen) {
  const f = doc.forms.form2;
  return {
    page: +f.ProgressPage.value,
    codes: classifyPage(doc, CODES).codes,
    names: [...doc.querySelectorAll('input:not([type=hidden]),select,textarea')].map(e => e.name),
    chosenValue: chosen,                 // 반드시 value. 라벨 금지
    nextAction: f.nextPageAction ? f.nextPageAction.value : null,
    gType: f.gType ? f.gType.value : null,
    accum: [...f.elements].filter(e => /^v\d+$/.test(e.name)).map(e => e.name + '=' + e.value)
  };
}
```

주행이 끝나면 `path = steps.map(s => s.codes[0])`를 만들고, 결정점마다
`transitions[문항][고른value]`가 다음 문항과 같은지 확인한다.

`accum`(v1..vN)을 함께 남기면 경로가 어긋났을 때 **어느 문항의 어느 응답이 분기를 틀었는지**를
재현 없이도 좁힐 수 있다.

### 무엇이 이상인가

- 결정점에서 같은 `value`를 골랐는데 **다음 문항이 세션마다 다르다** (비결정적 분기)
- 전이표에 없는 문항으로 갔다 / 도달해야 할 문항을 건너뛰었다
- 원안에 없는 분기가 웹에 있다, 또는 원안의 스킵 로직이 웹에 없다
- 배타 보기(`type='y'`)를 골랐는데 뒤 문항이 그대로 나온다
- 같은 문항으로 되돌아온다 (루프). 페이지 지문이 이전 스텝과 동일하면 즉시 경보

### 흔한 오탐과 구분법

| 증상 | 진짜 원인 | 구분법 |
|---|---|---|
| "예상 문항에 도달 못 함" | 라벨로 기록한 전이표가 애초에 틀림 | 전이표를 `value` 기준으로 다시 만들어 대조. 라벨 기반 전이표는 폐기 |
| "경로가 갑자기 끊김" | 순위형 토글 해제로 0개 선택 → 진행 불가 | 0.5의 서로 다른 인덱스 보장. 스텝 로그의 `chosenValue` 개수 확인 |
| "같은 문항 반복" | 필수응답 차단으로 제자리 POST | `window.alert` 수집 로그에 경고가 있으면 로직 이슈가 아니라 러너의 응답 누락 |
| "세션이 섞였다" | 대개 오해. 세션은 히든필드 기반이라 같은 브라우저에서 iframe 여러 개를 동시에 돌려도 안 섞인다(실측 확인) | 각 스텝의 `id`(CT…)가 세션 내내 동일한지 확인. 동일하면 섞임 아님 |

## 2. 이탈 — 종료 화면과 종료 문구

### 무엇을 보는가

이탈 조건(스크리닝 탈락, 쿼터 마감 등)을 만족하는 결정 벡터로 갔을 때
**종료 화면에 도달하는가**, 그리고 **그 화면의 문구가 원안의 이탈 문구와 같은가**.
반대로 이탈 조건이 아닌데 종료되지는 않는가.

### 어떻게 측정하는가

종료 화면 판정은 `classifyPage()`의 `END`다 — `#smtBtn`이 없고 입력 위젯이 0개.
여기에 다음을 함께 기록한다.

```js
function endInfo(doc, steps) {
  return {
    text: (doc.body.innerText || '').replace(/\s+/g, ' ').trim(),
    pathLen: steps.length,
    lastPage: +doc.forms.form2.ProgressPage.value,
    total: +doc.forms.form2.last_page.value,
    lastQuestion: steps[steps.length - 1].codes[0]
  };
}
```

원안의 이탈 문구·완료 문구를 `spec.json`에서 가져와 **정규화 후 포함 비교**한다
(공백 접기, 전각/반각 통일). 완전 일치를 요구하면 줄바꿈 차이로 전부 불일치가 된다.

### 무엇이 이상인가

- 이탈 조건인데 종료 화면이 안 나오고 계속 진행된다 (**HIGH** — 탈락자가 본조사에 유입)
- 이탈 조건이 아닌데 종료된다 (**HIGH** — 유효 응답자를 잃음)
- 종료는 맞는데 **문구가 반대다**: 탈락자에게 완료 문구, 완주자에게 "대상이 아닙니다"
- 이탈 종료 화면에 사례비·완료 안내가 같이 떠 있다 (문구 혼입)

**놓치기 쉬운 진짜 이슈:** 끝까지 다 답했는데 종료 문구가 "대상이 아닙니다"인 경우.
조기 이탈이 아니라 완주 후 이탈 처리라서 `pathLen`을 함께 봐야 잡힌다.
`pathLen`이 정상 완주 경로 길이와 같은데 종료 문구가 이탈 문구면 경보를 올린다.

### 흔한 오탐과 구분법

| 증상 | 진짜 원인 | 구분법 |
|---|---|---|
| "완주 후 이탈 종료" | **실측 1건은 재현되지 않은 일회성이었다** (2회 재시도 모두 정상) | 같은 결정 벡터로 독립 세션 2회 이상 재현. 재현 안 되면 제외하고 사유를 보고서에 남긴다 |
| "종료 화면인데 문구가 비었다" | 로드 직후 측정 (0.2 경쟁 조건) | `stabilize()` 통과 후 재측정 |
| "종료 문구 불일치" 대량 | 원안 문구에 서식·줄바꿈이 섞여 있음 | 정규화 후 비교. 그래도 다르면 원안 발췌를 증거에 넣어 보고 |
| "다음 버튼이 없다 = 종료" | 첫 진입 페이지는 버튼이 다르다: `href="javascript:form2.submit();"`, 텍스트 "조사참여 하기" | `#smtBtn` 부재만으로 판정하지 말고 `a[href*="form2.submit"]`도 함께 확인 |

## 3. 파이핑 — 앞 응답이 뒤 문구에 정확히 꽂히는가

### 무엇을 보는가

- 대괄호 안 문구(`[앞서 선택한 브랜드]`)가 **치환됐는가**, 아니면 그대로 노출되는가
- 치환된 값이 **앞서 실제로 고른 값과 같은가**
- 순위형 파이핑에서 **1순위·2순위가 뒤바뀌지 않았는가**
- "기타" 직접입력 값이 **입력한 문자열 그대로** 나오는가

### 어떻게 측정하는가

정답지는 히든필드 `v1..vN`에 있다. 주행 중 각 문항의 (문항코드 → `v` 이름 → 고른 value → 보기 텍스트)
매핑을 러너가 직접 만들어 들고 다닌다. 화면에서 텍스트를 다시 긁어 맞추려 하면
0.4의 라벨 추출 실패에 그대로 걸린다.

```js
// 주행 중 각 스텝에서 축적
answers[code] = { name: 'v12', value: '3', text: chosenTextOrNull, rank: null };
// 순위형이면
answers[code] = { name: 'v12', ranks: [{ value: '5', rank: 1 }, { value: '2', rank: 2 }] };
// 기타 직접입력이면
answers[code].otherText = '내가 입력한 문자열';
```

뒤 문항에서 검사한다.

```js
function checkPiping(doc, spec, answers) {
  const qText = questionTextOf(doc);                 // 문항 지시문 영역
  const left = qText.match(/\[[^\]]{1,40}\]/g) || []; // 치환 안 된 placeholder
  const expects = spec.piping[currentCode] || [];    // 예: [{from:'E1', kind:'rank1'}]
  const out = [];
  if (left.length) out.push({ code: 'PIPE_PLACEHOLDER_LEFT', found: left });
  for (const e of expects) {
    const a = answers[e.from];
    const want = e.kind === 'rank1' ? textOfValue(e.from, a.ranks[0].value)
              : e.kind === 'rank2' ? textOfValue(e.from, a.ranks[1].value)
              : e.kind === 'other' ? a.otherText
              : a.text;
    if (want && !qText.includes(want)) out.push({ code: 'PIPE_MISMATCH', expect: want, got: qText });
  }
  return out;
}
```

순위 뒤바뀜은 **1순위 값과 2순위 값이 서로 다른 시나리오**로만 판정할 수 있다.
Phase 4에서 순위형 문항이 있으면 1·2순위가 구분되는 시나리오를 반드시 넣는다.

기타 직접입력은 0.5의 순서(클릭 → 재조회 → 입력)를 지킨 세션에서만 검사한다.
순서를 어긴 세션의 `otherText`는 애초에 서버에 안 들어갔으므로 판정 대상이 아니다.

### 무엇이 이상인가

- `[...]`가 화면에 그대로 노출 (**HIGH** — 응답자가 미완성 화면을 본다)
- 다른 문항의 응답이 꽂힘, 또는 고르지 않은 보기가 꽂힘 (**HIGH** — 문항 의미가 바뀐다)
- 1순위 자리에 2순위 값 (**HIGH**)
- 기타 입력값이 공란이거나 다른 문자열로 바뀜
- 파이핑 대상이 복수 선택인데 하나만 나오거나 구분자가 깨짐(`A,,C`, `A、B`)

### 흔한 오탐과 구분법

| 증상 | 진짜 원인 | 구분법 |
|---|---|---|
| "파이핑 값 불일치" 대량 | 화면에서 긁은 보기 텍스트가 옆 보기까지 뭉쳐 잡힘 | 정답지를 **주행 중 기록한 value**로 잡고, 표시 텍스트는 참고만. `text: null`인 문항은 판정 보류(`text_unavailable`) |
| "기타 값이 안 나옴" | 기타 클릭 전에 텍스트를 채운 러너 버그 | 해당 세션의 조작 로그에서 클릭→입력 순서 확인. 어긋났으면 제외 |
| "대괄호 노출" | 원안 자체에 안내용 대괄호가 있는 경우(예: `[복수응답]`) | `spec.json`의 파이핑 참조 목록에 없는 대괄호 문자열은 **화이트리스트**로 등록해 무시 |
| "치환은 됐는데 값이 다름" | 앞 문항이 로테이션돼 화면 순서와 코드값이 다름 | value로 비교하면 사라진다. 라벨 순서로 비교했다면 그 판정 자체를 폐기 |

## 4. 로테이션 — 순서 다양성과 위치 분포

### 무엇을 보는가

- 노출할 때마다 보기 순서가 **바뀌는가** (고정돼 있지 않은가)
- 각 보기가 각 위치에 **고르게** 나오는가 (한쪽으로 쏠리지 않는가)
- **"기타"·"없음"·"해당사항 없음"이 항상 끝에 고정되는가**
- 원안에서 고정으로 지정한 보기가 실제로 고정인가

### 어떻게 측정하는가

DOM 순서대로 `value`를 뽑아 **순서 문자열**을 만든다. 표본은 서로 다른 세션에서 모은다.

```js
function orderKey(doc, name) {
  return [...doc.querySelectorAll(`input[name="${name}"]`)]
    .map(el => el.value).join('>');
}
```

세션 s의 문항 q에 대해 `orders[q].push(orderKey(...))`를 쌓고, 다음 세 지표를 계산한다.

1. **다양성** — `uniqueOrders / samples`
2. **위치 분포** — `count[value][position]` 행렬. 이상적으로는 각 칸이 `samples / n`
3. **말미 고정** — `kind`가 `other` / `exclusive`인 보기의 위치가 항상 마지막인가

```python
# scripts 쪽 집계 예시 (Python 3.12)
from collections import Counter, defaultdict

def rotation_report(orders, kinds, n):
    uniq = len(set(orders))
    pos = defaultdict(Counter)
    for o in orders:
        for i, v in enumerate(o.split('>')):
            pos[v][i] += 1
    tail_ok = all(
        o.split('>')[-1] in [v for v, k in kinds.items() if k in ('other', 'exclusive')]
        for o in orders
    ) if any(k in ('other', 'exclusive') for k in kinds.values()) else None
    return {"samples": len(orders), "unique": uniq, "pos": pos, "tail_fixed": tail_ok}
```

표본 수는 감으로 정하지 않는다. `references/coverage-design.md`의
`ln(n²/0.05) / ln(n/(n-1))`로 계산한 수를 채운 뒤에만 "로테이션 미작동"을 판정한다.

### 무엇이 이상인가

- 표본 수를 채웠는데 `unique == 1` → **로테이션 미작동** (원안이 로테이션 지정한 문항일 때)
- 원안이 고정인데 `unique > 1` → **로테이션이 잘못 걸림**
- `count[value][position]`에 **한 번도 등장하지 않은 칸**이 있고 표본이 충분함 → 부분 고정/편향
- `other` / `exclusive` 보기가 중간 위치에 나온 세션이 1건이라도 있음 → **말미 고정 실패**
- 행렬형에서 행은 로테이션되는데 열(척도)까지 같이 섞임

말미 고정은 **1건이라도 어긋나면 이슈**다. 통계 판정이 아니라 규칙 판정이다.

### 흔한 오탐과 구분법

| 증상 | 진짜 원인 | 구분법 |
|---|---|---|
| "보기 순서가 매번 같다" | 표본이 부족. 3~4회로는 n=5에서도 우연히 같을 수 있다 | 산정식으로 계산한 표본 수를 채우기 전에는 경보를 만들지 않는다 |
| "보기 순서가 뒤죽박죽" | 라벨 텍스트로 순서를 기록해 옆 보기와 뭉쳐 잡힘 | `value`로만 순서 기록. 라벨 기반 순서 로그는 폐기 |
| "기타가 끝이 아니다" | 라벨 텍스트로 "기타"를 찾다가 실패 | `onclick`의 `jFunRank` type(`t1`/`y`)으로 식별. 텍스트 매칭 금지 |
| "척도 문항 로테이션 미작동" | 척도는 대개 로테이션 대상이 아니다 | `spec.json`에 로테이션 지정이 없는 문항은 애초에 판정 대상에서 제외 |
| "보기 개수가 세션마다 다르다" | 앞 응답에 따라 보기가 파이핑되는 문항 | `spec.json`의 파이핑 참조 여부 확인. 해당되면 정상 |

## 5. 필수응답 — 무응답 제출이 차단되는가

### 무엇을 보는가

각 문항에서 **아무것도 고르지 않고 다음을 눌렀을 때** 진행이 막히는가.
막힌다면 어떤 경고 문구가 나오는가. 그리고 원안의 필수 지정과 일치하는가.

### 어떻게 측정하는가

이 엔진은 검증이 `embPageSet()` 하나에 모여 있다.
다음 버튼은 `<a id="smtBtn" onclick="if (embPageSet()){ form2.submit(); }">다 음</a>`이고,
검증 실패 시 `window.alert`로 경고를 띄운다.

따라서 **페이지를 이동하지 않고 검증만** 돌릴 수 있다. 이게 이 레이어를 고속으로 만드는 핵심이다.

```js
function probeRequired(win) {
  const msgs = [];
  const origAlert = win.alert, origConfirm = win.confirm;
  win.alert = m => { msgs.push(String(m)); };
  win.confirm = () => true;
  let passed = null;
  try {
    passed = !!win.embPageSet();   // 무응답 상태 그대로 검증만 호출
  } catch (e) {
    msgs.push('EXCEPTION:' + e.message);
  } finally {
    win.alert = origAlert; win.confirm = origConfirm;
  }
  return { passed, msgs };
}
```

`passed === true`면 무응답으로 통과한 것이고, `false`면 차단된 것이며 `msgs`에 경고 문구가 담긴다.
경고 문구는 레이어 6에서 그대로 재사용한다(문항번호 대조).

**주의:** `element.checked = true`로 강제 선택해 통과시키는 방식과 이 음성 테스트는 목적이 다르다.
음성 테스트는 반드시 **아무 조작도 하지 않은 상태**에서 호출해야 한다.
직전 문항의 잔여 선택이 남아 있으면 판정이 무의미해진다.

### 무엇이 이상인가

- 원안이 필수인데 `passed === true` → **무응답 통과** (HIGH, 데이터에 결측이 남는다)
- 원안이 선택응답인데 차단됨 → **과잉 필수** (HIGH, 응답자가 진행 불가)
- 최소/최대 선택 수 제약이 안 걸림 (복수응답에서 최대 3개인데 5개가 통과)
- 차단은 되는데 **경고 문구가 없다** (`passed === false`인데 `msgs`가 빔) → 응답자는 왜 안 넘어가는지 모른다
- 순위형에서 일부만 순위를 매겨도 통과

### 흔한 오탐과 구분법

| 증상 | 진짜 원인 | 구분법 |
|---|---|---|
| "필수인데 진행 불가" 대량(33건) | **순위형에서 같은 보기를 두 번 눌러 해제된 러너 버그** | 조작 로그에서 선택된 `RankTxt`의 `value` 개수 확인. 0개면 러너 탓 |
| "기타 선택 시 진행 불가" | 기타 클릭 전에 텍스트를 채운 러너 버그 | 클릭→재조회→입력 순서로 다시 주행. 재현 안 되면 제외 |
| "무응답인데 통과" | 직전 페이지의 선택이 남아 있거나 러너가 이미 채워 둠 | 호출 직전에 해당 문항 위젯의 선택 상태를 실제로 읽어 0개임을 증거에 기록 |
| "안내문 페이지에서 필수응답 미작동" | 안내문은 검증 대상이 아니다 | `classifyPage()`가 `INTRO`면 이 레이어를 건너뛴다 |

## 6. 문구 — 원안 대비 누락·오탈자·태그 노출

### 무엇을 보는가

- 원안에 있는 문항 지시문·보기 문구가 **웹에 그대로 있는가** (누락·축약·오탈자)
- **경고 문구의 문항번호가 실제 문항과 일치하는가**
- 문자 깨짐(모지바케), HTML 태그·엔티티 노출(`<br>`, `&nbsp;`, `&lt;`)
- 안내 문구와 실제 위젯 유형이 맞는가 ("1개 선택"인데 라디오가 없는 등)

### 어떻게 측정하는가

**문구 비교는 정규화 후 한다.** 정규화 없이 완전 일치를 요구하면 전부 불일치로 나온다.

```python
import re, unicodedata

def norm(s: str) -> str:
    s = unicodedata.normalize('NFKC', s)      # 전각/반각 통일
    s = s.replace(' ', ' ')
    s = re.sub(r'[ \t\r\n]+', ' ', s)
    s = re.sub(r'[“”]', '"', s)
    s = re.sub(r'[‘’]', "'", s)
    return s.strip()
```

검사 항목별 기법:

1. **누락·오탈자** — 원안 문구와 화면 문구를 `difflib.SequenceMatcher`로 비교해 유사도와
   차이 구간을 함께 남긴다. 유사도 1.0 미만이면 **차이 구간을 증거에 넣어** 사람이 판단하게 한다.
   자동으로 "오탈자 확정"을 찍지 않는다.
   > 진짜 이슈 사례: 척도 3번 보기가 **"보통 이였다"**. 원안은 "보통이었다"이므로 띄어쓰기와
   > 맞춤법이 모두 어긋났다. 유사도는 높지만 차이 구간이 명확해 사람이 즉시 확정할 수 있다.

2. **경고 문구 문항번호 대조** — 레이어 5에서 수집한 `msgs`에서 문항코드를 뽑아
   현재 페이지의 문항코드와 비교한다.
   ```js
   const inMsg = msgs.join(' ').match(/[A-Z]{1,3}\d+(?:-\d+)?/g) || [];
   const onPage = classifyPage(doc, CODES).codes;
   const mismatch = inMsg.filter(c => !onPage.includes(c));
   ```
   > 진짜 이슈 사례: **E2-1 페이지에서 미입력 시 경고가 "E2-2번에 입력해 주십시오"로 나왔다.**
   > 응답자는 화면에 없는 문항을 찾게 된다. `inMsg=['E2-2']`, `onPage=['E2-1']`로 자동 검출된다.

3. **문자 깨짐** — 이 엔진의 문자셋은 **EUC-KR이다(UTF-8 아님).** 브라우저는 자동 처리하지만
   **raw HTTP fetch로 받은 본문은 반드시 깨진다.** 따라서 깨짐 판정은 **브라우저가 렌더한 DOM의
   `innerText`에서만** 한다. `requests`나 `fetch`로 받아 디코딩한 문자열로 판정하면
   전 페이지가 깨짐 경보로 나온다 — 이건 100% 오탐이다.
   ```python
   MOJIBAKE = re.compile(r'[�]|[ÃÂ][\x80-\xBF]|(?:ìë)[^\s]{2,}')
   ```

4. **태그·엔티티 노출** — `innerText`(innerHTML 아님)에서 찾는다.
   ```js
   const leak = /<\s*\/?\s*(br|b|i|u|p|span|font|table|td|tr)\b|&(nbsp|lt|gt|amp|quot);/i
                  .test(doc.body.innerText);
   ```

5. **안내 문구 vs 위젯 유형** — 0.3의 `BROKEN_Q` 판정과 결합한다.
   > 진짜 이슈 사례: **"1개 선택"이라 안내하는데 보기가 하나도 없고 주관식 입력창만 있었다.**
   > 안내문에 "선택"/"개 선택"/"모두 고르"가 있는데 `input[type=radio]`와 `input[type=checkbox]`가
   > 0개면 경보. 반대로 "직접 입력"이라 안내하는데 `textarea`/`text`가 없어도 경보.

### 무엇이 이상인가

- 원안 문구가 통째로 빠짐, 보기 하나가 빠짐 (**HIGH** — 응답 분포가 달라진다)
- 경고 문구의 문항번호 불일치 (**HIGH** — 응답자가 진행을 못 한다)
- 안내 문구와 위젯 유형 불일치 (**HIGH** — 지시대로 응답할 수 없다)
- 오탈자·맞춤법 (**MED**)
- 태그·엔티티 노출, 문자 깨짐 (**MED**, 문항 지시문이면 HIGH)

### 흔한 오탐과 구분법

| 증상 | 진짜 원인 | 구분법 |
|---|---|---|
| "보기 텍스트 없음" **834건** | 척도형 스킨에 `<label>`이 없어 추출 실패. 화면에는 정상 표시 | input 개수로 교차확인. `count(input[name=X]) ≥ 1`이면 **경보 아님**, `text_unavailable` 표식만 |
| "응답 위젯 없음" **234건** | 안내문 페이지. 본문의 "응답해 주세요"를 문항 지시문으로 오인 | 0.3 분류기. 문항코드 사전에 걸리는 코드가 0개면 `INTRO` |
| "문자 깨짐" 전 페이지 | raw fetch를 UTF-8로 디코딩. 실제 문자셋은 EUC-KR | 브라우저 렌더 DOM에서만 판정. fetch 기반 깨짐 경보는 전량 폐기 |
| "문구 불일치" 대량 | 정규화 없이 비교 (전각 괄호, `&nbsp;`, 줄바꿈) | `norm()` 적용 후 재비교 |
| "경고 문구 문항번호 불일치" | 라벨 추출이 옆 보기까지 뭉쳐 잡아 엉뚱한 코드가 섞임 | 현재 페이지 코드는 **문항코드 사전 매칭**으로 구하고, `value`로 재확인 |
| "태그 노출" | `innerHTML`을 검사 대상으로 삼음 | 반드시 `innerText`로 검사 |

## 7. 진행률 — 역행·정체·조기 100%

### 무엇을 보는가

응답자에게 **표시되는** 진행률이 단조증가하는가, 특정 구간에 멈춰 있지 않은가,
마지막 문항 전에 100%에 닿지 않는가.

판정 기준은 **화면 표시값**이다. 히든필드 `ProgressPage`/`last_page`는 교차검증용이다.
응답자는 히든필드를 보지 않는다.

### 어떻게 측정하는가

매 페이지에서 표시값과 내부값을 함께 기록한다.

```js
function progressOf(doc) {
  const f = doc.forms.form2;
  const t = doc.body.innerText || '';
  const m = t.match(/(\d{1,3})\s*%/);
  let bar = null;
  for (const el of doc.querySelectorAll('[style*="width"]')) {
    const w = (el.getAttribute('style') || '').match(/width\s*:\s*(\d{1,3})%/);
    if (w) { bar = +w[1]; break; }
  }
  return {
    shown: m ? +m[1] : bar,
    page: +f.ProgressPage.value,
    total: +f.last_page.value,
    code: classifyPage(doc, CODES).codes[0] || null
  };
}
```

주행이 끝나면 시계열 `series = steps.map(progressOf)`에 대해 판정한다.

```python
def progress_issues(series, tail_slack=1):
    out = []
    for a, b in zip(series, series[1:]):
        if a["shown"] is not None and b["shown"] is not None and b["shown"] < a["shown"]:
            out.append(("PROG_BACKWARD", a["code"], a["shown"], b["code"], b["shown"]))
    for i, s in enumerate(series):
        if s["shown"] == 100 and i < len(series) - 1 - tail_slack:
            remain = [x["code"] for x in series[i+1:] if x["code"]]
            out.append(("PROG_EARLY_100", s["code"], remain))
            break
    return out
```

정체 판정은 임계값이 필요하다. 권장값은 **연속 5페이지 이상 표시값이 동일하고,
그 구간이 전체 페이지 수의 15% 이상**일 때 경보다. 이 값은 설문 길이에 따라 조정한다.
짧은 설문에서는 5페이지 연속이 정상일 수 있다.

### 무엇이 이상인가

- **역행** — 다음 페이지의 표시값이 이전보다 작다
  > 진짜 이슈 사례: **E2에서 78%였는데 E2-1에서 73%로 떨어졌다.** 하위 문항으로 들어가면서
  > 분모가 바뀐 것으로 보이며, 응답자에게는 "진행이 되돌아간" 것으로 보인다.

- **조기 100%** — 마지막 문항보다 앞에서 100%에 닿고 그 뒤로 문항이 더 남아 있다
  > 진짜 이슈 사례: **H1에서 이미 100%인데 H2·H3가 더 남아 있었다.** 응답자는 끝난 줄 알고
  > 창을 닫을 수 있다. 중도이탈로 직결되므로 심각도가 높다.

- **정체** — 긴 구간이 같은 값에 머문다 (분모가 실제 경로를 반영하지 않음)
- **표시값과 내부값의 방향이 반대** — `ProgressPage`는 늘었는데 표시값은 줄었다 (계산식 결함의 신호)

### 흔한 오탐과 구분법

| 증상 | 진짜 원인 | 구분법 |
|---|---|---|
| "진행률 급변" | 분기로 경로 길이가 달라지는 설계상 정상 동작 | **증가 방향의 급변은 경보 대상이 아니다.** 역행과 조기 100%만 판정 |
| "진행률 없음" | 안내문·종료 페이지에는 표시가 없을 수 있다 | `shown is None`인 스텝은 시계열에서 제외하고 앞뒤를 이어 비교 |
| "100% 뒤에 페이지가 있다" | 마지막이 완료 안내 페이지인 정상 케이스 | `tail_slack`으로 종료/완료 안내 페이지를 허용. **문항코드가 있는 페이지**가 뒤에 남을 때만 경보 |
| "역행" 1건 | 로드 직후 이전 페이지의 바를 읽음 | `stabilize()` 통과 후 측정. 페이지 지문이 바뀐 것을 확인하고 나서 진행률을 읽는다 |
| "역행"이 특정 세션에만 | 진짜일 가능성이 높다 | 같은 결정 벡터로 독립 세션 재현. E2→E2-1 사례는 재현되어 확정됐다 |

## 이슈 등급 기준

등급은 **응답자 노출도**를 1축, **응답자가 겪는 결과**를 2축으로 판정한다.
"고치기 어려운가"는 기준이 아니다. 연구원이 개발자에게 우선순위를 전달하기 위한 축이다.

### 노출도

| 구분 | 정의 |
|---|---|
| 전원 | 모든 응답자가 반드시 지나가는 페이지 |
| 다수 | 흔한 분기에 있어 상당수가 지나가는 페이지 |
| 조건부 | 특정 보기를 고른 사람만 도달 |
| 희소 | 드문 조합에서만 도달 |

### 결과

| 구분 | 정의 |
|---|---|
| 차단·오염 | 진행 불가, 잘못된 이탈/미이탈, 응답 데이터가 틀리게 저장될 소지 |
| 혼란 | 지시대로 응답할 수 없음, 잘못된 안내로 응답자가 헤맴, 중도이탈 유발 |
| 미관 | 읽는 데 지장은 없으나 품질이 떨어짐 |

### 판정 행렬

| | 차단·오염 | 혼란 | 미관 |
|---|---|---|---|
| **전원 / 다수** | HIGH | HIGH | MED |
| **조건부** | HIGH | MED | LOW |
| **희소** | MED | LOW | LOW |

### 등급별 정의와 실측 사례

**HIGH — 응답자가 직접 겪고, 응답이 막히거나 틀어진다.**
- 진행 불가 / 무응답 통과 / 잘못된 이탈·미이탈 / 경로가 원안과 다름
- 파이핑 값이 틀림, 대괄호 placeholder 노출
- 진행률 역행 — *실측: E2 78% → E2-1 73%*
- 조기 100% 이후 **문항이 2개 이상 남음** — *실측: H1에서 100%, 이후 H2·H3*
- 경고 문구의 문항번호 불일치 — *실측: E2-1 페이지에서 "E2-2번에 입력해 주십시오"*
- 안내 문구와 위젯 불일치 — *실측: "1개 선택" 안내인데 보기 없이 주관식 입력창만*
- 로테이션 대상 문항의 말미 고정 실패("기타"/"없음"이 중간에 노출)

**MED — 응답에 영향을 줄 수 있으나 진행은 된다.**
- 오탈자·맞춤법 — *실측: 척도 3번 보기 "보통 이였다"*
- 안내 문구 일부 누락, 원안과 표현 차이
- 로테이션 미작동(원안이 로테이션 지정, 분포 편향)
- 조기 100%인데 남은 문항이 **1개**뿐
- 태그·엔티티 노출(보기 문구 영역)
- 조건부 경로에서만 나타나는 혼란성 결함

**LOW — 사용성·일관성 수준. 확인 권장.**
- 진행률 정체
- 페이지 간 문구 스타일 불일치, 띄어쓰기 편차
- 희소 경로에서만 재현되는 미관 결함
- 원안에 명시 없는 구현 선택(보고는 하되 결함으로 단정하지 않음)

### 등급을 올리거나 내리는 조건

- 재현율 100%(모든 시도에서 발생)이고 노출도가 전원이면 **한 단계 올린다**
- 2회 이상 시도 중 1회만 재현되면 **한 단계 내리고 재현율을 명시한다**
- 재현이 전혀 안 되면 등급을 매기지 않고 **제외 내역**에 넣는다
  > 실측: "완주 후 이탈 종료" 1건은 2회 재시도에서 재현되지 않아 제외했다

## 오탐 처리 규약

### 재현 프로토콜

모든 경보는 다음을 통과해야만 확정 이슈가 된다.

1. 경보를 **유형(code) × 문항**으로 묶는다. 1,107건이 10여 개 유형으로 접힌다
2. 유형마다 대표 경보의 **결정 벡터를 그대로 재사용해 독립 세션**을 새로 띄운다
   (히든필드 기반 세션이므로 같은 브라우저의 별도 iframe으로도 완전히 독립적이다 — 실측 확인)
3. **2회 이상 재현**되면 확정. 1회만이면 등급을 낮추고 재현율을 병기
4. 재현 과정에서 원인이 러너 조작으로 밝혀지면 **러너를 고치고 다시 돌린다**.
   러너 버그로 판명된 경보는 이슈가 아니다
5. 제외한 것은 **건수와 사유**를 보고서에 남긴다

### 실측 오탐 대응표 (요약)

| 경보 | 건수 | 진짜 원인 | 차단 지점 |
|---|---|---|---|
| 응답 위젯 없음 | 234 | 안내문 페이지 오인 | 0.3 페이지 분류기 (문항코드 사전) |
| 보기 텍스트 없음 | 834 | 척도형 스킨에 `<label>` 부재 | 0.4 value 개수 교차확인 |
| 빈 페이지 | — | 로드 직후 경쟁 조건 | 0.2 `stabilize()` 200ms 재확인 |
| 진행 불가(막힘) | 33 | 순위형 토글 해제(같은 인덱스 2회) | 0.5 서로 다른 인덱스 보장 |
| 기타 선택 시 진행 불가 | — | 기타 클릭 전 텍스트 입력 | 0.5 클릭→재조회→입력 순서 |
| 완주 후 이탈 종료 | 1 | 재현 불가(일회성) | Phase 7 재현 2회 |

앞의 다섯 가지는 **탐지기·러너를 고쳐서 애초에 경보가 안 나게 만드는 것**이 정답이다.
Phase 7에서 매번 손으로 걸러내는 방식은 다음 프로젝트에서 또 1,000건을 만든다.

### 정상 확인 항목도 기록한다

경보가 없었다는 사실 자체가 산출물이다. 레이어별로 **검사한 문항 수 / 통과 수 / 판정 보류 수**를
집계해 보고서의 "정상 확인 항목"에 넣는다. 판정 보류(`text_unavailable`, 표본 부족 등)를
통과로 섞으면 커버리지가 부풀려진다. 반드시 분리한다.

## 근거가 된 실측 사례

### 확정된 진짜 이슈

| # | 증상 | 레이어 | 등급 |
|---|---|---|---|
| 1 | E2-1 페이지에서 미입력 시 경고가 "E2-2번에 입력해 주십시오"로 나옴 (문항번호 불일치) | 6 (수집은 5) | HIGH |
| 2 | E2 78% → E2-1 73% 진행률 역행 | 7 | HIGH |
| 3 | H1에서 이미 100%인데 H2·H3가 더 남음 | 7 | HIGH |
| 4 | "1개 선택" 안내인데 보기가 없고 주관식 입력창만 있음 | 6 (분류는 0.3) | HIGH |
| 5 | 척도 3번 보기 "보통 이였다" 맞춤법 오류 | 6 | MED |

### 이 문서가 지키려는 숫자

- 경보 1,107건 → 확정 이슈 10건. **오탐률 99%**
- 오탐의 96%가 두 가지 원인(안내문 오인 234건 + 라벨 추출 실패 834건)에서 나왔다.
  0.3과 0.4의 두 절이 이 문서에서 가장 값이 나가는 부분이다
- 페이지당 평균 178ms, 10개 동시 주행으로 50 시나리오/1,358 페이지를 185초에 완주.
  **재현 검증을 몇 번 더 돌릴 시간은 충분하다.** 오탐을 안 거를 이유가 없다
